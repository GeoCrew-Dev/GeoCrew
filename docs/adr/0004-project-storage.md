# 0004 工程存储：每个工程一个 GeoPackage

## 背景

旧版的所有工程共用一个 Room 数据库，几何存成 GeoJSON 文本，以"记录"为中心，没有图层，也没有空间索引。要做完整的 GIS，数据就得改成以图层为中心。

## 决定

- **每个工程一个文件夹**：`/sdcard/GeoCrew/工程/<名称>/`，里面有工程的 GeoPackage 和 `附件/` 目录。
- **以图层为中心**：工程由图层组成。每个图层有几何类型、字段、坐标系、样式和表单。
  - 字段带稳定的 ID，改名不影响同步合并，见 [ADR 0008](0008-sync-and-merge.md)。
  - 每个图层可以用任意坐标系，按原坐标保存。
- **图层模板**：地质点、路线、剖面、钻孔等做成内置的图层模板。野外定点仍保留专门的快捷流程，底层写进"地质点"图层。
- **附件**：
  - 文件放在 `附件/` 下，按 SHA-256 命名，同一个文件只存一份，同步也只传一次。
  - GeoPackage 里有一张附件表，用"关联表扩展"（Related Tables Extension）登记成一对多关系。
- **导出附件**：
  - GeoPackage：可以选"附件打包进库"；
  - KMZ：照片打包进去；
  - Shapefile、GeoJSON、CSV：在字段里写相对路径，附件放在旁边的文件夹，一起打成 zip。
- **数据安全**：
  - GeoPackage 里记录格式版本；
  - 打开工程时检查完整性；
  - 每天用 SQLite 的备份接口自动做一份快照，保留最近 N 份；
  - 从 v0.1 起，升级不丢数据，迁移都有测试。
- **SQLite 的设置**（M1 验证补充）：
  - 工程 GeoPackage 用 WAL 日志模式。SQLite 默认的 DELETE 模式在 /sdcard 上每次提交都要经过 FUSE 建、删日志文件，逐条保存慢 10 倍。
  - 同步级别明确设成 FULL（`OGR_SQLITE_SYNCHRONOUS=FULL`），每次保存都 fsync，突然断电也不丢已保存的点；实测每条约 2 ms。GDAL 对新建的文件默认不做 fsync，不设的话断电时可能损坏刚导入的文件。
  - 导出、分享或拷贝工程前先做 WAL 检查点；工程开着时，最近的修改还在 `-wal` 文件里。
  - 导入时先把要素写完，再执行 SQL：在写入前执行的 SQL 会让 GDAL 提前建好空间索引，逐条维护，慢十几倍。
- **同步中的工程只由应用写入**。外部程序只能读；要改，就改导出的副本。因为用 WAL，外部程序要读的是已关闭或刚做过检查点的工程；工程开着时直接读 `.gpkg`，会看不到还在 `-wal` 里的修改。
- 旧版的 Room 数据不做迁移，因为是重写，也没有用户。

## 理由

- GeoPackage 是 GDAL 的原生格式，带空间索引，桌面 GIS 能直接打开，符合"开放格式、数据自主"的原则。
- 一个工程一个文件夹，方便拷贝、备份、交给别人。

## 代价与后果

- /sdcard 和外置卡都走 FUSE。M1 在模拟器上实测：用 WAL 时逐条保存一个点约 2 ms（私有目录 1.3 ms），导入 10 万点约 0.3 秒，随机杀进程后都能完整恢复，见[验证报告](../spikes/m1-gpkg-sdcard.md)。
- FAT32 的卡上单个文件最大 4 GB。
- 退路：真机上如果明显变差，工作库放在应用私有目录，/sdcard 上放自动导出的副本。
- 待定：同步用的元数据放在 GeoPackage 的扩展表里，还是放在单独的文件里，M2 设计编辑缓冲时一起定。

## 状态

已采纳（2026-11-25）。M1 在模拟器上验证通过，见[验证报告](../spikes/m1-gpkg-sdcard.md)；真机和 exFAT 存储卡上的复测还没做。
