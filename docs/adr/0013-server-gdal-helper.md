# 0013 服务端的 GDAL 辅助程序

## 背景

图层可以用任意坐标系之后，服务端的网页查看页、KML / GPX 导出、AI 的"附近搜索"都需要做坐标转换，导出格式也越来越多。负责人同意服务端加入 GDAL。

但服务端现在是纯 Go 的（SQLite 用的是 modernc），可以随意交叉编译成单个可执行文件。直接引入 CGO 会让五个平台的构建都变复杂，GDAL 一旦崩溃，还会把同步服务一起拖垮。

## 决定

- **同步核心保持纯 Go**，继续用 modernc 的 SQLite。
- **GDAL 做成单独的辅助程序**，服务端在导出和坐标转换时调用它，作为子进程运行，链接 GeoCrew-Native 编出的静态库。
- **发布平台**：linux amd64 / arm64、darwin amd64 / arm64、windows amd64，不再支持 32 位（ARMv7）。
- 某个平台的辅助程序编不出来时，同步服务照样发布，只是依赖 GDAL 的功能不可用。

## 理由

- 把 CGO 的复杂性和崩溃风险都隔离在一个小程序里，同步服务的构建和稳定性不受影响。

## 代价与后果

- 要多发布一个程序，Docker 镜像里两个都带上。
- 子进程调用有启动开销，只适合导出、批量转换这类不频繁的操作。
- 待定：频繁的坐标转换（比如网页查看页显示非经纬度图层）是由客户端顺带上传经纬度副本，还是由辅助程序常驻处理，要结合协议 v1 设计（M2）。
- PROJ 和 GDAL 的数据文件要随程序一起分发。

## 状态

草案。M1 要验证"辅助程序在五个平台上的静态构建"。
