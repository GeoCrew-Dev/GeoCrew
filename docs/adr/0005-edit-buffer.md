# 0005 编辑缓冲与就地编辑

## 背景

负责人要求能在原文件上直接改外部数据，这是很重要的功能。但 GDAL 没有通用的"编辑会话"：只有部分驱动支持事务（GPKG、SQLite、PostgreSQL、OpenFileGDB），Shapefile、MapInfo 都没有。撤销、编辑日志和崩溃恢复都得我们自己做。

## 决定

- **自己做一个编辑缓冲**：
  - 每次改动先写进编辑日志表，再改到数据上；
  - 支持撤销和重做；
  - 应用崩溃后，可以从日志恢复没保存的修改；
  - 保存时写回驱动，驱动支持事务的就放在事务里。
- **工程图层和外部图层共用这一套。** 工程图层的同步也建在它上面，靠它记录变更，见 [ADR 0008](0008-sync-and-merge.md)。
- **能做哪些编辑，按 GDAL 报告的驱动能力决定**：随机写入、删除要素、增加字段、事务支持。
- **按格式分三类**：
  - 能逐条修改的（GPKG、SQLite、Shapefile、FileGDB、MapInfo 等）：真正的就地编辑。首批只做 GPKG 和 Shapefile，其他格式逐步开放。
  - 保存时整个文件重写的（GeoJSON、CSV 等）：用起来一样，只是保存慢一些。
  - 驱动只会写新文件的（KML、GPX、DXF）：只能"另存覆盖"。覆盖前自动备份，并提示原文件里我们不认识的内容（比如 KML 的样式和文件夹结构）可能丢失。
- **格式本身的限制照旧**：Shapefile 字段名最长 10 个字符，删除后压缩会重排要素编号，单个文件不能超过 2 GB。
- **外部图层由一个人编辑**。要给组员用，可以"加入工作组"转成工程图层，或者改完写回原文件。共享数据库（如 PostGIS）的在线编辑放到以后做。

## 理由

用一套缓冲同时管撤销、崩溃恢复和同步变更记录，比给就地编辑和同步各做一套机制简单。

## 代价与后果

- 编辑缓冲是核心部件，要单独设计和测试，属于 M2 的关键路径。
- 不同格式能做到的程度不一样，界面上要按驱动能力来开关功能。

## 状态

已采纳（2026-11-25）。

2026-11-26 补充：负责人定了编辑按 QGIS 的逻辑来。

- 图层要先"开始编辑"。改动先放在编辑缓冲里，按"保存"才写回数据，按"放弃"就全部丢掉。工程图层和外部图层都这样，工程图层也不自动保存。
- 新要素在保存前用负数编号，保存后换成驱动给的编号。
- 撤销、重做按图层分开，只管这次编辑里还没保存的改动，保存或放弃后清空。撤销栈仍然只在动作注册表里（ADR 0010），按图层分组；编辑缓冲只负责记下每次改动前后的样子。
- 保存按 QGIS 的顺序写回：先改已有要素的属性和几何，再删要素，最后加新要素；字段的增、删、改名以后加上，排在最前面。
  - 驱动支持事务的，整次保存放在一个事务里，失败就全部回滚，编辑缓冲原样保留。这一点比 QGIS 默认的做法稳妥。
  - 不支持事务的，已经写进去的改动从缓冲里去掉，没写成的留下，和 QGIS 一样。
- 和 QGIS 不同的一点：每次改动先落盘到应用私有目录的日志里，再改缓冲。应用被杀或崩溃后再打开，能恢复没保存的改动，但撤销记录不恢复。日志不放进用户的数据文件。
- 同步只发已经保存的改动。野外定点的快捷流程要不要"加一个点就保存一次"（QField 的做法），做那个流程时再定。
