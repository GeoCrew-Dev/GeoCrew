# 0008 同步与合并（协议 v1）

## 背景

v0 的合并规则会丢数据。两人都基于同一个版本修改时，落败一方的离线修改会被丢掉，而且不会进修改历史。另外，比较时先看版本号，所以离线多改几次的人总会赢。改成以图层为中心以后，要同步的东西还多了图层结构和附件。

## 决定

- **协议升到 v1**，不兼容 v0。
- **一切都是"表里的行"**，每行带全局 UUID；删除的行留下墓碑。要素、附件、样品都按这个规则处理，不再有"列表取并集"这类特例。
- **服务端按字段做三方合并**。客户端提交时带上 `base_seq`，也就是它基于服务端的哪个版本修改的。
  - **改了不同字段**：两边的修改都保留。
  - **改了同一个字段**：后改的为准。编辑时间用服务端时钟换算：`服务端当前时间 −（客户端当前时间 − 编辑时间）`，换算后时间相同的，按到达服务端的先后定。几何整体算一个字段。
  - **落败的值不丢**：写进冲突记录，这条要素标为"有冲突"，组长或当事人点一下就能换成另一个值。
  - **一人删除、一人修改**：保留修改，并提示删除的人。
- **图层结构变更**：
  - 字段带稳定的 ID；
  - 改结构只能在线做，并带版本号；
  - 改到已删除字段上的编辑，进冲突记录。
- **优先级**：离线队列的可靠性 > 晚上回驻地后的批量同步和冲突处理界面 > 实时功能。"谁在编辑"这类实时提示放到后面做。
- **测试**：
  - 做随机交错测试，保证任何一次编辑要么在结果里，要么在冲突记录里；
  - 合并规则用一份 Go 与 Kotlin 共用的测试样例：`protocol/testdata/merge/cases.json`；权限规则的在 `protocol/testdata/permissions/cases.json`。Go 在 `server/internal/merge`、`server/internal/perm`，Kotlin 在安卓的 `core:sync`（2026-11-28），两边都读同一份样例。
- **附件**分块上传，支持断点续传，先传缩略图。

## 理由

- 带上基准版本，按字段合并，加上冲突记录，修改就不会悄悄丢失。
- 用服务端时钟换算时间，可以避开手机时钟不准的问题。
- 只保留"行内按字段合并 + 墓碑"这一种规则，最简单，也最好测试。

## 代价与后果

- 客户端要保存每条脏数据所基于的版本。服务端要保存历史，用来做三方合并。
- 协议文档、服务端和新客户端都要按 v1 重写。v1 文档在 M2 写，实现在 M3 完成。
