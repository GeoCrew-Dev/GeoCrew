# 0008 同步与合并（协议 v1）

## 背景

v0 的合并规则会丢数据。两人都基于同一个版本修改时，落败一方的离线修改会被丢掉，而且不会进修改历史。另外，比较时先看版本号，所以离线多改几次的人总会赢。改成以图层为中心以后，要同步的东西还多了图层结构和附件。

## 决定

- **协议升到 v1**，不兼容 v0。
- **一切都是"表里的行"**，每行带全局 UUID；删除的行留下墓碑。要素、附件、样品都按这个规则处理，不再有"列表取并集"这类特例。
- **服务端按字段做三方合并**。客户端提交时带上 `base_seq`，也就是它基于服务端的哪个版本修改的。
  - **改了不同字段**：两边的修改都保留。
  - **改了同一个字段**：后改的为准。编辑时间用服务端时钟换算：`服务端当前时间 −（客户端当前时间 − 编辑时间）`，换算后时间相同的，按到达服务端的先后定。几何整体算一个字段。
  - **落败的值不丢**：写进冲突记录，这条要素标为"有冲突"，组长或当事人点一下就能换成另一个值。
  - **一人删除、一人修改**：保留修改，并提示删除的人。
- **图层结构变更**：
  - 字段带稳定的 ID；
  - 改结构只能在线做，并带版本号；
  - 改到已删除字段上的编辑，进冲突记录。
- **优先级**：离线队列的可靠性 > 晚上回驻地后的批量同步和冲突处理界面 > 实时功能。"谁在编辑"这类实时提示放到后面做。
- **测试**：
  - 做随机交错测试，保证任何一次编辑要么在结果里，要么在冲突记录里；
  - 合并规则用一份 Go 与 Kotlin 共用的测试样例：`protocol/testdata/merge/cases.json`；权限规则的在 `protocol/testdata/permissions/cases.json`。Go 在 `server/internal/merge`、`server/internal/perm`，Kotlin 在安卓的 `core:sync`（2026-11-28），两边都读同一份样例。
- **附件**分块上传，支持断点续传，先传缩略图。

## 理由

- 带上基准版本，按字段合并，加上冲突记录，修改就不会悄悄丢失。
- 用服务端时钟换算时间，可以避开手机时钟不准的问题。
- 只保留"行内按字段合并 + 墓碑"这一种规则，最简单，也最好测试。

## 代价与后果

- 客户端要保存每条脏数据所基于的版本。服务端要保存历史，用来做三方合并。
- 协议文档、服务端和新客户端都要按 v1 重写。v1 文档在 M2 写，实现在 M3 完成。

## 状态

已采纳（2026-11-25）。

2026-11-28 补充：客户端的修改记录（M3）。

- 编辑缓冲给每个字段记下最后一次编辑的时间（几何和删除也算，手机时钟的毫秒），和修改一起写进日志，崩溃后找得回。
- 保存时，在写要素的同一个事务里把改过的字段交给存储层（`LayerStore.saved`），要素和待上传的修改要么都存下，要么都没存。
- 工程连了工作区（`geocrew_project` 里有 `workspace`）才记，没连的什么都不记。记在工程文件的两张新表里，第一次需要时才建：
  - `geocrew_rows`：图层 ID、fid、行 UUID、基准 `seq`（服务端还没有的是 0）；
  - `geocrew_outbox`：行 UUID、图层 ID、字段 ID、值（JSON）、编辑时间（UTC，到毫秒）。字段用 `geocrew_fields` 里的稳定 ID，几何记作 `geom`，删除记作 `deleted`。同一字段只留最后一次编辑。
- 工作区还没有的要素整条上传：新要素，以及连工作区之前就有、第一次修改的要素（从文件读出全部字段）。工作区从没有过的要素，删了也不用告诉它。新要素没给值的字段，编辑时间用这条要素最近一次编辑的时间。
- 上传成功后清掉对应的条目、更新 `seq`，由协议客户端做（M3 的下一步）。

2026-11-28 再补充：共享工程和提交（M3）。

- 共享：在服务端建工作区（创建人是组长），把工程的每个图层按原来的 ID 建成共享图层（字段用 `geocrew_fields` 的 ID），连上工程，再把已有的要素全部当新行放进待上传。中途断了可以重来：已经建好的图层、已经排上的要素都不重复。混合几何（`GEOMETRY`）的图层暂时不能共享。
- 账号（服务器地址、工作区、成员和令牌）按工程 ID 存在应用自己的目录里（`no_backup/sync/`），不进工程文件，因为工程文件会被拷走、发给别人。
- 提交：先把待上传的修改按行打包成"发送中"的修改（`geocrew_sending`：修改 ID、行、图层、基准 `seq`、修改的内容），一行一条；这期间再改的字段回到 `geocrew_outbox`，等这一条被服务端收下再打包。按服务端的 `max_push_batch` 分批发；网络断了，下次原样重发（修改 ID 不变，服务端认出是重试）。`applied`、`duplicate` 的清掉；被拒的（`rejected`）留在手机上、记下原因，不再自动重发（协议 4.6）。

2026-11-28 第三次补充：加入和拉取（M3）。

- 加入：用邀请码（新成员）或转移码（同一成员的新手机）加入后，新建一个以工作区命名的本地工程（重名加编号），连上工作区，再拉取全部内容。加入前工程里不能有没保存的修改，否则先不加入。
- 拉取：从上次拉到的 `seq`（存在 `geocrew_project` 的 `pulled_seq`）开始一页页拉，写完一页再记下新的 `seq`，中途断了重拉这一页结果一样。
  - 工程里没有的共享图层按原 ID 建成本地图层，字段的 ID 也照搬；已删除的共享图层、字段的增删改名暂时不处理（随结构同步一起做）。
  - 行直接写进图层文件，不经过编辑缓冲，所以不会被当成本机的修改再传回去。本机还没传上去的字段（在待上传或发送中）保留本机的值，其余字段、几何、删除和恢复照服务端的写。
  - 每行的基准 `seq` 记成这一页的 `seq`，本机下次改这一行就从它算。
  - 冲突记录存进 `geocrew_conflicts`，给冲突列表用。
- "立即同步"先提交、再拉取；有没保存的修改时只提交不拉取（写进文件的行会和编辑缓冲冲突），返回里 `pulled` 为空。

2026-11-28 第四次补充（附件上传）：

- 保存时，要素的附件有增删改，就在同一个事务里记进修改记录：附件行按协议 9.1 属于系统表 `attachments`，行 ID 就是附件自己的 UUID，字段是 `target_layer`、`target_row`、`file`、`thumb`、`type`、`size`、`name`、`meta`。新附件整条记，改了的只记改的字段，拿掉的记删除；要素被删时附件行不动，要素恢复时跟着回来。
- 附件行的基准 `seq` 记在 `geocrew_attachment_rows`（UUID、`seq`），和 `geocrew_rows` 记要素的一样。
- 新附件的原图和缩略图记进待上传的文件（`geocrew_uploads`：哈希、类型、是不是缩略图）。同步时先传缩略图，再提交修改（附件行排在它挂的要素行后面，服务端只认已有的行），最后传原图；每次同步传文件的时间有上限，没传完的下次从断点接着传。
- 本机新建的行，建它的修改被收下时就用返回的 `seq` 作基准（协议 8.2 的例外），不用等拉取。

2026-11-28 第五次补充（附件下载）：

- 拉到的附件行（系统表 `attachments`）按 `target_layer`、`target_row` 挂到本机的要素上：新的加上，改了的换掉，删了的拿掉，记下它的 `seq`。本机还有修改没传上去的附件行不动。要素还没到的附件行（要素在附件之后又改过，按 `seq` 排在后面；或者要素被删后又恢复）先存进 `geocrew_pending_attachments`，之后拉到新的行时再挂。
- 拉取完下载缺的缩略图，每次最多 20 秒；原图在打开时下载（动作 `sync.file`），先写到旁边的 `.part` 文件，断了下次接着下，哈希对上才放到附件目录。原图还没上传的，打开时显示缩略图。
- 拉取时，本机还有字段没传上去的行，除了保留本机的值，基准 `seq` 也先不变：要是改成这一页的 `seq`，别人同时改的同一字段就会被当成本机看过的，本机的值提交上去时悄悄把它盖掉（协议 8.2）。

2026-11-28 第六次补充（图层的样式和顺序）：

- 图层按协议 7.1 也是一行（系统表 `layers`，行 ID 是图层 ID），`style` 和 `order` 像字段一样记进修改记录、合并。系统表的行（附件和图层）的基准 `seq` 都记在 `geocrew_system_rows`（原来叫 `geocrew_attachment_rows`，还没发过版本，直接改名）。
- `order` 是图层在本机绘制顺序（`Project.layers`，第一个画在最上面）里的位置。排序、移动、建组、拆组之后，位置变了的图层记一条；拉到时把这些图层按位置从小到大放回去，分组和只在本机的图层留在原处。共享时每个图层带上样式和位置，记下建图层返回的 `seq`。
- 拉到的样式直接写进 `geocrew_layer_style`，不经过检查用户输入的 `setStyle`（更新的手机可能多带了别的设置），也不再记进修改记录。
- 字段 ID 只在图层内唯一（协议 7.2）：`geocrew_fields` 改成 `UNIQUE (table_name, id)`，以前的工程在建共享图层时重建这张表。

2026-11-28 第七次补充（离线改结构，Fable 受负责人委托定）：

- 加字段、建图层可以离线做：字段 ID 和图层 UUID 都由新增的一方生成，和别人同时做的结构变更不冲突。只含 `add_field` 的结构请求服务端不比对版本，重发同一个不报错，ID 定义不同返回 `id_taken`。
- 改字段名、改选项、删字段只能在线做，仍按 `base_version` 比对：离线排队只会带来后写覆盖或悄悄丢弃。
- 字段名在图层内唯一（去掉首尾空格、不分大小写）。两人离线各加同名字段时，后提交的一方收到 `name_taken`：定义相同就改用已有的 ID，不同就换个名字再提交并告诉用户。
- 理由：野外整天没信号时也要能加"样品编号"这样的字段，否则数据只能塞进描述或记在纸上。协议 7.1、7.3、7.4 已按此改写。
