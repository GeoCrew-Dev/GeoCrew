# 同勘 GeoCrew 开发计划独立评审（2026-11-25）

> 由 Fable 5.2 子代理只读评审，未改动任何文件。依据：全部计划记录，以及 roadmap.md、protocol-v0.md（§4.3 等）、releases.md、device-test.md、两份 README、GeoCrew-Native/README.md、Server 的 go.mod。联网核对了三处：MapLibre Native 三维地形、Let's Encrypt IP 证书、GDAL 算法注册表。其余标"未核实"的判断来自经验，要靠技术验证确认。

## 1. 总体评价

- 四个方向的技术选型大体站得住：GDAL 栈、一个工程一个 GeoPackage、动作注册表、基于 base_seq 的三方合并、用户自带 Key，都是成熟路线，没有做不到的硬伤。
- 最大的风险是重演上一轮的失败：铺得很宽、CI 全绿、却没人在真机上用过。现在的计划写清了"怎么做"，但没有写"v0.1 到底包含什么"和"怎样才算做完"。
- 有三样东西被当成了现成能力，其实要自己写：
  - GDAL 没有通用的"编辑会话"；
  - MapLibre Native 官方至今没有三维地形；
  - "QGIS 能做的"大部分在 QGIS 自己的代码里，不在 GDAL 里。

  这三项都属于工作量，不是做不到，但要按工作量排期。
- 还没人定的两件事，都应在 v0.1 前有结论：
  - 国内合规：备案主体、离线底图里的国界画法、隐私弹窗；
  - 数据安全：自动备份、格式版本。
- 下面的建议以分期和做减法为主，不推翻已定的决策。

## 2. 必须修改或补充

**2.1 v0.1 的范围和"完成"的定义没有定**

- 问题：只说"v0.1 前冻结功能"，没说 v0.1 包含什么，也没说新分支何时取代 main。旧版 README 的功能清单极长，重写很容易变成逐项照搬。
- 理由：没有范围，AI 代理会再次铺开；没有完成的定义，"CI 绿"又会被当成"能用"。
- 建议：
  - v0.1 只做一条纵向闭环：建工程 → 天地图底图 → 地质点（产状、照片）→ 编辑 → 导出 GPKG / KML → 两台手机经服务端同步，且不丢数据。
  - 旧功能清单整理成"对等清单"，分成 v0.2 / v0.3 / 以后三档。
  - 完成定义里写明：负责人在真机上走通，并留下录屏或日志。
- 涉及：仓库与流程。

**2.2 测试策略和 AI 代理的护栏**

- 问题：计划只写了"PR + 分支保护"，没有针对"无人审查、没上真机"这个已知失败模式的措施。本机现在没有 Go，也没有 Android SDK。
- 理由：负责人未必逐行看代码，质量只能靠机器测试加真机验收。
- 建议：
  - **同步测试**：同步引擎做随机交错测试，要守住的不变量是"任何一次编辑，要么在结果里，要么在冲突记录里"。
  - **共用测试向量**：合并、权限、版本比较各用一份 Go 与 Kotlin 共用的测试向量。
  - **渲染对比**：两个渲染器用同一批样式做截图对比。
  - **CI**：用 x86_64 模拟器跑仪器测试。
  - **野外验收**：每个里程碑安排一次两台手机的野外验收，device-test.md 的条目逐项留证据。
  - **代理规则**：写进各仓库的 CLAUDE.md：
    - 一次只做一个纵向切片；
    - PR 限制大小；
    - 引入新依赖前先写 ADR；
    - README 只列真机验证过的功能，没验证的标"实验"。
  - **准备工作**：先装好本地工具链，定下测试机型。
- 涉及：仓库与流程。

**2.3 "GDAL 编辑会话"不是 GDAL 的现成能力**

- 问题：计划把外部图层的就地编辑写成"通过 GDAL 编辑会话"。实际上：
  - GDAL 只对部分驱动有事务（GPKG、SQLite、PG、OpenFileGDB），Shapefile、MapInfo 没有；
  - 撤销、落盘日志、崩溃恢复都要自己写一个编辑缓冲，QGIS 里的同类功能也是它自己写的。
- 理由：这是外部图层的核心部件，不是一个配置项。
- 建议：
  - 单独立项做"编辑缓冲"：改动先写进日志表，保存时再写回驱动。
  - 工程图层和外部图层共用这一套，同步的变更跟踪也建在它上面，省掉一套机制。
  - 首批只支持 GPKG 和 Shapefile 就地编辑，其他格式按驱动能力逐步开放。
- 涉及：GIS。

**2.4 "QGIS 能做的都有类似功能"需要一份能逐项核对的清单**

- 问题：GDAL / PROJ / GEOS 只覆盖读写、投影和几何运算。QGIS 的处理工具箱、标注引擎、符号系统、版面、拓扑检查都是 QGIS 自己的代码，等于都要我们自己写。
- 理由：按负责人的口径这属于"工作量"，但量极大，必须排出先后。
- 建议：
  - 章程里列一份分档清单：
    - 第一档：采集和编辑，对齐 QField；
    - 第二档：处理工具箱里最常用的约 50 个工具；
    - 第三档：版面和高级符号。
  - GDAL 的算法注册表确实可以拿来自动登记工具：`gdal --json-usage` 和 C++ 注册表从 3.11 起可用，C 接口的文档写的是从 3.12 起。建议锁定 GDAL ≥ 3.12。
  - 要清楚，GDAL 的算法数量远少于 QGIS 工具箱。
- 涉及：GIS。

**2.5 "后改的赢"没有说用哪个时钟**

- 问题：手机时钟可能不准，离线编辑也可能隔天才上传。v0 的丢数据缺陷里，就有"版本号高的赢，哪怕它编辑得更早"这一条。
- 理由：输的一方会进冲突记录，所以不会丢数据；但规则必须确定、可以测试。
- 建议：
  - 客户端上传"编辑时间"和"上传时的本机时间"，服务端用自己的时间换算：`服务端当前时间 −（客户端当前时间 − 编辑时间）`。
  - 换算后时间相同，按到达服务端的先后定。
  - 几何整体算一个字段。
  - 这些规则都写进协议和共用测试向量。
- 涉及：协作。

**2.6 列表"取并集"可以整个去掉**

- 问题：列表取并集，意味着删掉某一项的操作永远传不出去，除非再加墓碑标记。
- 理由：附件已经设计成 GPKG 关联表里的行，样品也可以这样做。
- 建议：协议 v1 里一切都是"表里的行"，每行带一个全局 UUID。合并规则只保留一种："行内按字段合并 + 删除的行留墓碑"，去掉列表取并集这个特例。
- 涉及：协作、GIS。

**2.7 改图层结构和离线编辑撞上时，规则还没定**

- 问题：组员离线改要素时，组长把字段删了、改了名或改了类型，怎么处理没有规则。另外两件事也没定：同步用的元数据放在哪；同步中的工程 GPKG 能不能被 QGIS 等外部程序改写。
- 理由：以图层为中心以后，改结构成了常规操作，发布后再改规则代价最大。
- 建议：
  - 字段带稳定的 ID，改名不影响合并。
  - 改结构只能在线做，并带版本号。
  - 指向已删除字段的编辑进冲突记录。
  - 明确写一条：同步中的工程 GPKG 只由应用写入，外部程序只能读；要改就导出一份副本再改。
- 涉及：协作、GIS。

**2.8 用户数据的备份、损坏恢复和格式版本**

- 问题："不做数据迁移"只对这次重写成立。v0.1 以后的格式升级、单个 GPKG 损坏后的恢复、自动备份都还没提。
- 理由：野外数据没法重采。文件放在 /sdcard，可能被别的应用、文件管理器或用户误删，突然断电也可能写坏。
- 建议：
  - 打开工程时做完整性检查。
  - 每天自动做一次快照（用 SQLite 的备份接口），保留最近 N 份。
  - 在 GPKG 里记下格式版本。
  - 从 v0.1 起承诺"升级不丢数据，迁移有测试"。
  - 保留"工程包导出导入"，作为没有服务端时的交换手段。
- 涉及：GIS、仓库与流程。

**2.9 国内合规要先给出结论**

- 问题一：上国内应用商店要做 App 备案，多数商店还要求软著，这都需要一个备案主体。本项目没有中心服务器，备案挂在谁名下还没定（各商店的现行细则未核实）。
- 问题二：如果项目自己分发基于 OSM 的中国范围离线底图和地名库，有"问题地图"的风险，比如国界、台湾、南海、藏南的画法。
- 问题三：隐私方面缺几样：首次启动的隐私政策弹窗（同意之前不申请任何权限）、后台定位的说明、个人信息清单。把数据发给境外模型接口属于数据出境，需要告知用户。
- 问题四："用 IP 加端口就不用备案"只是常见做法，不是法律结论，文档里不要写成承诺。
- 建议：
  - 项目方不托管、也不分发中国范围的 OSM 底图和地名库，只提供让用户自备或自己生成的工具。国内默认用天地图，并显示审图号。
  - 天地图瓦片能不能离线缓存，要查它的服务条款（未核实）。
  - v0.1 前写一页合规清单。
  - 走哪些分发渠道由负责人拍板（见 6.1）。
- 涉及：地图、协作、AI、仓库与流程。

**2.10 缺少安全与威胁模型**

- 问题：
  - 应用持有全部文件访问权限，同时又要解析来路不明的文件。
  - AI 会读到组员消息、导入图层的属性和插件说明书，这些都可能被用来做提示注入；其中插件说明书按设计会直接进入 AI 手册。
  - Key 和令牌放在哪里没有规定。
  - "隔离进程"具体指什么不清楚。
- 理由：安卓的 isolatedProcess 没有任何文件权限，只能接收传进来的文件描述符，处理不了 Shapefile 这类多文件格式和目录格式。普通的独立进程只能防崩溃，防不住漏洞利用。
- 建议：
  - 明确目标只是防崩溃，用普通的独立进程即可，不追求防漏洞利用。
  - Key 和令牌只放在应用私有目录，用 Keystore 保护；不进 /sdcard，不进工程包，也不进图源分享的 JSON 或二维码。
  - 插件工具的风险分组，由宿主按插件声明的权限推出一个下限，插件不能自己往低报。
  - AI 触发的导出、分享、联网、删除，一律先确认。
  - 服务端代理的日志默认只记用量，不记对话内容。
  - 服务端的 GDAL 放在子进程里跑（同一个可执行文件，用子命令启动），GDAL 崩了不会拖垮同步服务。
- 涉及：GIS、AI、插件、协作。

**2.11 动作注册表缺少稳定性规则**

- 问题：同一个动作的 ID 和参数，同时被六个地方用到：AI 工具、插件 API、MCP、用户自定义按钮、规则、灵宝的训练集。改一个动作，六处一起坏。
- 理由："手册自动生成"能保证文档同步，保证不了兼容。
- 建议：
  - 每个动作标一个稳定级别：稳定、预览、内部。
  - 只有"稳定"级的动作开放给插件、MCP 和训练集。
  - 稳定动作的参数只能增加、不能改；改名时保留旧名作为别名。
  - 从行走骨架的第一天起，所有界面操作都要走注册表。旧版有 11 个文件绕过了它。
- 涉及：AI、插件。

## 3. 建议考虑

**3.1 两个渲染器共用一个样式模型：先定两边的交集**

- 问题：MapLibre 只支持 Web 墨卡托，符号按像素算；制图渲染器要支持任意坐标系，符号按毫米算；两边的标注引擎也不一样。所以两边画出来不可能完全一样。
- 建议：
  - 样式模型 v1 只收两边都能实现的部分：单一、分类、分级、规则（SQL 条件）四种方式，配点、线、面、标注，再加地质符号库。
  - 只有出图才用得上的属性单独标出来。
  - 制图渲染器直接画到 Android 的 Canvas 和 PdfDocument 上，输出就是矢量 PDF。
  - 用截图对比测试把两边的差异控制住。
- 涉及：GIS。

**3.2 实时地图怎么出图，要写清楚**

- 问题：
  - "表达式在生成瓦片时求值"，意味着要把 GPKG 现场切成瓦片再交给 MapLibre。怎么切片、编辑后怎么只刷新改动的部分，都没写。
  - 非 3857 的栅格和 WMTS（比如天地图 `_c` 经纬度瓦片、本地高斯投影的 GeoTIFF），MapLibre 不能直接显示，要先用 GDAL 重投影成瓦片。
- 建议：
  - 先用 MapLibre Android 的 CustomGeometrySource：按瓦片范围查 R 树，重投影后返回要素，这是最省事的路线。
  - 不够快再自己编码 MVT。
  - 把"非 3857 栅格显示"列入技术验证。
- 涉及：GIS、地图。

**3.3 三维地形：不要指望 MapLibre Native 官方**

- 问题：已核实。到 2026 年的官方通讯仍然说，Native 的三维地形停在原型分支 `feature/terrain-3d`，没有正式发布；只有 GL JS 有地形。
- 建议：
  - 取消这一项技术验证。
  - 三维直接用 WebView 加 MapLibre GL JS 做一个只读视图，以后再做。
  - 实时等高线也没有现成的原生实现，要自己用 GDAL 从 DEM 生成。
- 涉及：地图。

**3.4 GeoPackage 放在 /sdcard 上，要先测**

- 问题：共享存储走 FUSE，SQLite 在上面的 WAL 性能和可靠性都比应用私有目录差，外置 SD 卡（exFAT）更差（未实测）。
- 建议：
  - 加一项技术验证：10 万要素的写入、崩溃后能否恢复、外置卡上的表现。
  - 不达标的话，最简单的退路是工作库放在私有目录，/sdcard 上放自动导出的副本。
  - 全部文件访问权限在国内商店要写明用途，负责人已经知道。
- 涉及：GIS。

**3.5 服务端加 GDAL 的代价要算清楚**

- 问题：
  - 服务端现在用纯 Go 的 SQLite（modernc），可以随意交叉编译。加了 CGO 之后，五个目标平台都要有原生的构建机。
  - 静态链接 glibc 有坑。
  - PROJ 需要 proj.db，GDAL 也需要数据文件，"单文件部署"只能靠把它们内嵌进去、首次启动时解包。
- 建议：
  - 同步核心保持纯 Go。GDAL 只在导出和重投影的子进程里用（同 2.10），这样即使 GDAL 构建出问题，同步服务也照样能发布。
  - 把"五个平台的静态构建"列入技术验证。
  - Linux 用 musl，或者只静态链接依赖库。
  - vcpkg 的 Android 三元组是可行的，QField 就是这么做的，可以参考它的端口。
- 涉及：协作、仓库与流程。

**3.6 权限模型：协议一次做全，界面分期做**

- 问题：层级、叠加、按图层覆盖、"只改自己的要素"，再加约 20 项权限，对 5 到 20 人的野外小组偏重；离线时客户端还得自己再判断一遍权限。
- 建议：
  - 协议和服务端按已定方案一次做全。
  - 首版界面只给三个预设身份（组长、组员、只读），外加"图层只读"。
  - 自定义身份的编辑器放到 v0.3 以后。
  - 权限判断用一份 Go 与 Kotlin 共用的测试向量。
- 涉及：协作。

**3.7 AI 的三种模式和自由布局界面：分期做**

- 问题：
  - "演示给我看"和"带我做"要求每个动作都绑定到具体的页面和控件，界面还没稳定时做，会反复返工。
  - 按钮可以任意拖动和缩放的话，文档、截图、教学模式都失去了固定的参照。
- 建议：
  - 先只做"直接做"加确认卡。
  - 界面定制先做"快捷栏可增删、可排序"，自由摆放和缩放放到后面。
  - 另外两种模式等界面稳定后再加。
- 涉及：AI。

**3.8 自签证书和网页查看页、MCP 冲突**

- 问题：证书固定只对手机有效。浏览器打开查看页会报警告，桌面上的 MCP 客户端大多不接受自签证书。证书到期、IP 变了怎么办，也没有提。
- 建议：
  - 固定公钥而不是整张证书，这样 IP 变了不用重新邀请。
  - 另给一条可选路线：有公网 IP 的服务端，用 ACME 自动申请 Let's Encrypt 的 IP 证书。已核实这项服务 2026 年 1 月正式可用，有效期约 6 天，需要自动续期。国内云的 80 / 443 端口是否放行，未核实。
  - 文档里写明：家用宽带大多没有公网 IPv4，实际需要一台云主机。
- 涉及：协作。

**3.9 "离线优先"和"暂缓野外连接"同时成立时，先做什么**

- 问题：野外多数时间没有信号，真实的用法是晚上回驻地后批量同步。实时在线状态、"谁在编辑"的提示，价值不高。
- 建议：
  - 优先级排成：离线队列的可靠性 > 晚间批量同步和冲突处理界面 > 实时功能。
  - "谁在编辑"推到后面。
  - 没有服务端时，用工程包文件交换兜底。
- 涉及：协作。

**3.10 后台轨迹在国产系统上能不能活下来**

- 问题：这是野外工具的命门，旧版从没在真机上验证过。小米、OPPO、vivo、华为的省电策略都会杀后台；Android 14 起，前台服务还要声明类型。
- 建议：
  - 列入第一批技术验证：三四个品牌的手机，各锁屏走两小时。
  - 应用里给出各品牌加"电池白名单"的引导。
- 涉及：地图。

**3.11 插件引擎：把调试放到电脑上，绕开 QuickJS 的短板**

- 问题：QuickJS 没有 JIT，也没有调试协议。把克里金这类数值计算写成 JS 插件会很慢，也和"沿用已测过的 Kotlin 算法"冲突。
- 建议：
  - 插件 API 设计成纯异步的消息接口。插件在电脑上的 Node 里连接无头宿主调试，手机上只需要日志和热重载。
  - 数值计算多的算法留作内置动作。
  - 做示范的官方插件选"编排类"的，比如三点法、地层厚度。
  - QuickJS 的技术验证不在 v0.1 的关键路径上，可以往后放。
- 涉及：插件。

**3.12 列一份许可证与数据条款清单**

- 问题：
  - GDAL 的可选依赖里有 GPL 的（poppler、librttopo、MySQL 客户端等）。
  - GEOS 是 LGPL，静态链接时要保证用户能重新链接。本项目完全开源就能满足，但闭源的分叉不行。
  - 数据也有条款：OSM 是 ODbL（衍生数据库要同样共享并署名），Copernicus DEM 要署名，模型权重各有各的许可。
- 建议：
  - Native 仓库在 vcpkg 的特性清单里明确排除 GPL 依赖，CI 里检查许可证。
  - 安卓上把 GEOS 编成单独的 .so。
  - 发布包附上第三方声明，README 里已经有这个承诺。
- 涉及：仓库与流程、地图。

**3.13 仓库数量：7 个偏多**

- 问题：协议、服务端、客户端经常要一起改，分在三个仓库就没法在一个 PR 里原子地改完，AI 代理跨仓库协作的成本也高。
- 建议：
  - 考虑把 Protocol、Server、Android、Docs 合成一个主仓库。Native（构建久）、Plugins（要收外部 PR）、网站（仓库名是固定的）各自独立，一共 4 个。
  - 新建的四个仓库还没提交，现在改最便宜。
  - 提交前先解决 git 身份对不上的问题。
- 涉及：仓库与流程。

**3.14 崩溃诊断、版本兼容、多语言、性能预算：各写一页**

- **崩溃诊断**：不建中心上报。崩溃日志存在本机，原生崩溃用系统的 ApplicationExitInfo 拿到；提供"导出诊断包"，可以选择上报到团队自己的服务端。
- **版本兼容**：
  - releases.md 里已经有更新机制。
  - 还缺一张兼容表：应用、协议、服务端、Native、插件引擎之间哪些版本能配在一起。
  - 还缺"组里一半人更新了"时怎么办。1.0 之前可以规定全组一起升级，并给出清楚的提示。
  - 签名密钥要有备份方案。
- **多语言**：从第一天起，所有界面文字都放进资源文件，默认中文，英文以后补。
- **无障碍**：先做强光下的高对比主题和手套模式。动作注册表里自带的名称，可以直接当读屏标签用。
- **性能预算**：定一台低端参考机型（三防机常用较弱的芯片），再定几个目标值：APK 体积、冷启动时间、10 万要素时的帧率、8 小时轨迹的耗电。
- 涉及：仓库与流程。

## 4. 以后再说

**4.1 同勘灵宝**

- 速度表偏乐观（未实测）：在手机 CPU 上，2k token 的冷启动预填充可能要 10 秒以上，中端机和三防机更慢。野外有风噪，语音识别出的错多半比模型出的错更主要。
- 等规则解析加云端这条路有了真实的使用日志，再做基准测试。模型仓库到时再建。
- 涉及：AI。

**4.2 Python 内核、WASM、原生插件应用**

原生插件应用的绑定服务需要签名校验和用户授权，到时再设计。涉及：插件。

**4.3 完整的插件目录生态**

吊销列表、镜像、"AI 写插件"、上架 CI 里跑提示词测试，都放到以后。先用三个官方插件自己用起来。吊销列表拉不到时是放行还是禁用，到时再定。涉及：插件。

**4.4 PostGIS 等共享数据库的在线编辑与签出签入、点云**

手机端加 libpq 会增大体积，需求也还没验证过。涉及：GIS。

**4.5 驻地局域网、组长手机当服务器、厂商推送、短信报位置**

已经定了暂缓，同意。涉及：协作。

**4.6 HarmonyOS NEXT 和 iOS**

见 6.3。如果答案是"以后要做"，现在唯一要做的，就是把同步、样式、合并规则都写成协议文档和测试向量，不绑死在 Kotlin 里。涉及：仓库与流程。

## 5. 建议的里程碑顺序

关键路径：**Native 的 GDAL 构建 → GPKG 图层模型与编辑缓冲 → 出图管线 → 采集闭环 → 协议 v1 的同步合并**。

**M0 治理（1–2 周）**

- 章程，包括 v0.1 的范围和分档的对等清单。
- ADR、各仓库的 CLAUDE.md、分支保护。
- 本地工具链、测试机型、git 身份。
- 合规清单和威胁模型各一页，再加一份许可证清单。

**M1 技术验证**（限时，可以并行；每一项都写明失败后的退路）

- 用 vcpkg 编出 GDAL 的 AAR，看 APK 体积。
- /sdcard 上的 GPKG。
- 用 CustomGeometrySource 出图：10 万要素，加编辑后的刷新。
- 非 3857 栅格的显示。
- 服务端五个平台的 CGO 静态构建。
- 天地图 Key 的类型和水印。
- 后台轨迹在国产系统上能否存活。
- 不在关键路径上、往后放的：QuickJS、三维、端侧模型。

**M2 单机行走骨架**

- 工程、GPKG、图层模型、编辑缓冲与撤销。
- 动作注册表：所有操作从第一天起都走它。
- 天地图底图加工程图层的显示。
- 地质点采集：罗盘、用 CameraX 拍照。
- 用 GDAL 导入导出。
- 自动备份。
- 可以同时进行：写协议 v1 文档；服务端重建表结构和合并逻辑（纯 Go，配共用测试向量，不依赖 GDAL）。
- 出口标准：负责人带到野外实际用一天。

**M3 协同 = v0.1**

- 协议 v1 的同步、按字段合并、冲突记录和冲突处理界面。
- 附件分块、断点续传。
- 三个预设身份。
- 证书固定。
- 出口标准：随机交错测试通过；两台手机的野外验收通过；新分支取代 main。

**M4 广度 = v0.2–0.3**（GIS 和地图两条线并行）

- GIS：外部图层的就地编辑、样式与表达式、处理工具（GDAL 算法）、导出 PDF 地图、任务管理器。
- 地图：图源引擎、离线 PMTiles 底图和 DEM、卫星状态、RTK、步行导航。

**M5 AI = v0.4**

- 统一的模型客户端、"直接做"模式、规则、语音。
- 服务端代理与额度。
- 自动生成手册、MCP 写操作。
- 离线口令解析可以提前，跟着 M2 / M3 顺带做。

**M6 插件预览 = v0.5**

- 引擎验证、运行时、SDK、无头宿主、三个官方插件、插件目录。

**M7 走向 1.0**

- 完整的身份权限界面、自由布局、"演示给我看"和"带我做"两种模式。
- 三维（用 WebView）。
- 灵宝的基准测试。
- 冻结插件 API。

## 6. 需要负责人拍板的问题

1. **分发渠道和主体**：只走 GitHub、Gitee 和官网直装，还是也要上国内应用商店？上商店的话，App 备案和软著用谁做主体？
2. **谁来审代码**：您本人看代码吗？如果不看，能否接受"另一个 AI 来评审 + 您只做真机验收"？手上有哪几台测试手机？能不能安排两个人去野外实测？
3. **平台**：HarmonyOS NEXT（新款华为手机装不了 APK）和 iOS，是永远不做、以后做，还是现在就要留出余地？
4. **v0.1 的范围**：2.1 里的那条闭环够不够？哪些旧功能您认为 v0.1 必须有？
5. **AI 排在什么时候**：按第 5 节，完整的 AI 放在 M5，只有离线口令可以提前。您是否要求 AI 更早进来？
6. **不做 GCJ-02**：奥维的多数用户用的是高德或谷歌中国影像，这些图在同勘里会偏几百米，这是"超过奥维"这个目标下最大的体验代价。是否还坚持"连显示时的纠偏也不做"？
7. **离线底图**：是否同意项目方不分发中国范围的 OSM 底图和地名库，只提供让用户自备的工具？
8. **权限和界面分期**：是否同意 3.6 和 3.7，也就是协议一次做全，界面先给预设身份，自由布局以后再做？
9. **仓库**：是否考虑 3.13 的合并，7 个变成 4 个？
10. **工程 GPKG 只能由应用写**：同步中的工程文件，是否允许用户用 QGIS 等直接改写？建议不允许。
11. **服务端代理的日志**：组长能看到组员和 AI 的对话内容，还是只能看到用量？
12. **最低配置**：最低支持哪个 Android 版本？低端参考机型选哪一款？
