# 协议一致性检查

从外部（只用 HTTP 和 WebSocket）检查一个服务端是否按[协议 v0](../docs/protocol-v0.md)工作。自己实现服务端、改了官方服务端，或者升级前想确认新版本没有破坏客户端，都可以跑一遍。

```
go run github.com/GeoCrew-Dev/GeoCrew-Protocol/conformance@latest -server https://geo.example.org
```

需要 Go 1.22 以上，不依赖第三方库。每项检查一行，前面标出对应的协议章节；有失败时退出码为 1，可以直接放进 CI。加 `-v` 会同时列出跳过的检查和原因。

它会做这些事：

- 读 `/healthz` 和 `/api/v0/info`，按 `capabilities` 决定跑哪些检查（没声明的能力跳过）；
- 新建一个名为 `conformance 日期 时间` 的工作组，再用小写邀请码加入一位组员；
- 检查鉴权和错误格式、组长和组员各自看到的信息、提交与重复提交、同一请求里 id 重复、`updated_by` 由服务端填写、按 `version`、`updated_at` 定胜负和 `stale` 带回当前版本、历史版本、分页拉取和删除、只读角色、最后一位组长、共享设置的版本和 `409 stale`、附件的 201 / 204 / HEAD / 哈希不符 / Range、实时通道的 `hello`、位置转发和 `feature_changed`，以及声明了相应能力时的讨论（重试、`409 id_conflict`、删除留痕）、紧急消息、点名和查看链接（只读、越界时长、撤销）；
- 最后重置邀请码并吊销那位组员。

注意：

- 服务端必须允许新建工作组（声明 `create`）；关闭了新建的实例上大部分检查会跳过。请在测试实例上运行，不要对正式服务器跑。
- 协议没有删除工作组的接口，检查完会留下这个工作组（组员已吊销）；官方服务端可以用运维命令清理，或者直接用一个临时数据目录。
- 新建和加入按客户端地址限流，遇到 `429` 会按 `Retry-After` 等一次再试。

本仓库的 CI 会拉取官方服务端最新代码，用临时数据目录启动后跑这套检查，协议文档和服务端实现一旦对不上就会发现。
