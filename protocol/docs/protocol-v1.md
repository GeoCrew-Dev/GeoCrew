# 同勘 GeoCrew 协同协议 v1（草案）

> 状态：草案，M2 期间逐节写，M3 实现。依据 [ADR 0008](../../docs/adr/0008-sync-and-merge.md)（同步与合并）和 [ADR 0009](../../docs/adr/0009-roles-and-permissions.md)（身份与权限）。v1 不兼容 v0，v0 的客户端不再支持；[v0 文档](protocol-v0.md)在 v1 写完之前只作参考。v1 的接口在 M3 实现时一并写进 [`openapi.yaml`](openapi.yaml)；在那之前，`openapi.yaml` 描述的仍是现行的 v0。

## 1. 和 v0 的主要区别

- 以图层为中心：数据都是图层里的"行"，每行带全局 UUID，字段用稳定的字段 ID 作键，改名不影响合并。
- 按字段合并：客户端只提交改过的字段，服务端按字段做三方合并；落败的值写进冲突记录，不再整条覆盖。
- 编辑时间换算到服务端时钟，手机时钟不准不会影响谁胜出。

## 3. 行与合并

### 3.1 行

- 每行属于一个图层，有全局唯一的 UUID，由创建它的客户端生成。
- 字段的键是图层结构里的字段 ID，不是字段名。几何是一个名为 `geom` 的字段，值是 GeoJSON 几何对象，坐标用图层的坐标系；几何整体算一个字段。
- 服务端为每个字段记四样东西：值、最后修改人、编辑时间（换算到服务端时钟，见 3.3）、最后修改它的序号 `seq`。
- 删除也按字段记：`deleted` 的值为 `true` 或 `false`。删除的行保留全部字段（墓碑），可以恢复。

### 3.2 提交一条修改

客户端每次只提交自上次同步以来改过的字段：

```json
{
  "row": "8d3c6f0e-0c1a-4d7e-9a43-3f1d9b0f4e21",
  "base_seq": 5,
  "client_now": "2026-11-25T12:00:00Z",
  "set": {
    "f1": { "value": "D001", "edited_at": "2026-11-25T11:50:00Z" },
    "geom": { "value": { "type": "Point", "coordinates": [114.0, 30.0] }, "edited_at": "2026-11-25T11:50:00Z" }
  },
  "delete": { "value": true, "edited_at": "2026-11-25T11:55:00Z" }
}
```

| 字段 | 说明 |
|---|---|
| `base_seq` | 客户端最后一次看到这一行时，服务端的序号；新建的行为 `0` |
| `client_now` | 发出请求时客户端的时钟 |
| `set` | 改过的字段，各带新值和客户端记下的编辑时间；没改的字段不要带 |
| `delete` | 可选。`true` 删除，`false` 恢复；值不是布尔值的请求被拒绝 |

修改人由服务端按鉴权身份填写，不由客户端提供。请求的整体格式、批量提交和响应在"基本约定"和接口章节里写。

### 3.3 编辑时间

服务端把客户端的编辑时间换算到自己的时钟：

> 编辑时间（服务端）= 服务端收到请求的时间 −（`client_now` − `edited_at`）

换算结果晚于服务端当前时间的，按服务端当前时间算。

### 3.4 合并规则

服务端逐个字段处理 `set` 里的修改。字段的 `seq` 大于 `base_seq`，说明客户端修改之后别人也改过它，称为"并发修改"。

1. **没有并发修改**（服务端还没有这个字段，或它的 `seq` 不大于 `base_seq`）：直接采用新值。
2. **有并发修改，值相同**：不变，不算冲突。值按 JSON 比较，忽略格式和对象键的顺序。
3. **有并发修改，值不同**：编辑时间晚的为准；时间相同的，后到达服务端的为准。落败的值写进冲突记录（`value`）。
4. **字段已从图层删除**：这次修改写进冲突记录（`deleted_field`），其余字段照常处理。

删除和恢复：

5. **删除**：`base_seq` 之后没有任何字段被改过，才删除；否则不删，删除写进冲突记录（`delete_rejected`），提示删除的人。
6. **别人删除了这一行**（删除发生在 `base_seq` 之后），而这次修改改了字段：字段照常合并，这一行恢复，那次删除写进冲突记录（`delete_overridden`），提示删除的人。恢复记在这次修改名下：修改人是提交者，时间是服务端收到请求的时间，序号是这次修改的序号。
7. **恢复**：已删除的行，`delete` 为 `false` 时恢复。

### 3.5 冲突记录

```json
{ "kind": "value", "field": "f1",
  "kept": { "value": "from m2", "by": "m2", "at": "2026-11-25T11:30:00Z", "seq": 9 },
  "lost": { "value": "from m1", "by": "m1", "at": "2026-11-25T11:00:00Z", "seq": 7 } }
```

| `kind` | 什么时候 | `lost` 是 |
|---|---|---|
| `value` | 规则 3 | 落败的值（可能是服务端原来的值，也可能是这次提交的值） |
| `deleted_field` | 规则 4 | 这次提交的值 |
| `delete_rejected` | 规则 5 | 这次提交的删除 |
| `delete_overridden` | 规则 6 | 别人的那次删除 |

- 一次修改产生的冲突，先按字段 ID 排序列出字段冲突，再列删除冲突。
- 有未处理冲突的行标为"有冲突"。组长或当事人可以一键换成另一个值；换值就是一次普通修改，按同样的规则合并。

### 3.6 共用测试样例

合并规则的测试样例在 [`protocol/testdata/merge/cases.json`](../testdata/merge/cases.json)，服务端（`server/internal/merge`）和安卓客户端都必须逐条通过。每条样例给出服务端当前的行、一次修改和期望的结果；服务端当前时间、序号和图层现有字段取文件开头的默认值，个别样例另行指定。

服务端另有随机交错测试：几个时钟不准的客户端交替离线修改、删除、恢复和提交，检查任何一次提交的值要么进了行，要么进了冲突记录。

## 4. 图层与结构变更

### 4.1 图层

图层本身也是一行，属于系统表 `layers`，有全局唯一的 UUID。它的属性分两类：

- **按第 3 节合并的字段**：`name`（名称）、`style`（样式，JSON，见 [ADR 0006](../../docs/adr/0006-rendering-and-styles.md)）、`form`（表单布局，JSON）、`order`（图层顺序，数字）。可以离线改，和普通行的字段一样合并。`style` 和 `form` 各自整体算一个字段：两人同时改了样式的不同部分，也按同一字段处理，落败的那份进冲突记录。
- **结构**：几何类型 `geometry_type`、坐标系 `crs`、字段定义 `fields` 和结构版本 `schema_version`。只能在线改，见 4.3。

| 结构 | 说明 |
|---|---|
| `geometry_type` | `Point`、`LineString`、`Polygon`、`MultiPoint`、`MultiLineString`、`MultiPolygon`，或 `None`（没有几何的表）。创建后不能改 |
| `crs` | 创建时定，`EPSG:代码` 或 WKT2 文本；创建后不能改，要换坐标系就新建图层再导入。几何坐标按这个坐标系，轴顺序一律东、北（经度、纬度） |
| `fields` | 字段定义的列表，见 4.2 |
| `schema_version` | 结构版本，从 1 开始，每次结构变更加 1 |

共享工作区里的图层要在线创建：创建请求带上初始结构，`schema_version` 为 1。离线时只能在本地工程里建图层，本地工程加入工作区时再上传（工作区一节待写）。

### 4.2 字段

```json
{ "id": "f3k9x2", "name": "岩性", "type": "string", "options": ["花岗岩", "灰岩"] }
```

| 属性 | 说明 |
|---|---|
| `id` | 由新增字段的一方生成，1 至 64 个字符（字母、数字、`_`、`-`），在图层内唯一，删除后也不再使用。行里的字段用它作键（第 3 节）。`geom` 留给几何，不能用 |
| `name` | 显示名，可以改；改名不影响已有数据，也不影响合并 |
| `type` | 见下表；创建后不能改 |
| `options` | 可选。取值列表，界面上显示成选择框 |

| `type` | JSON 中的值 |
|---|---|
| `string` | 字符串 |
| `integer` | 整数，范围 ±(2^53 − 1)：超出这个范围时很多 JSON 解析器会丢精度，更大的编号请用 `string` |
| `real` | 数字 |
| `boolean` | `true` 或 `false` |
| `date` | 字符串，`2026-11-25` |
| `datetime` | 字符串，RFC 3339，例如 `2026-11-25T11:50:00Z` |
| `json` | 任意 JSON 值 |

任何类型的值都可以是 `null`，表示没有填。

### 4.3 结构变更

```
POST /api/v1/workspaces/{ws}/layers/{layer}/schema
```

```json
{
  "base_version": 3,
  "ops": [
    { "op": "add_field", "field": { "id": "f7q2m1", "name": "采样编号", "type": "string" } },
    { "op": "rename_field", "id": "f3k9x2", "name": "岩石名称" },
    { "op": "set_options", "id": "f3k9x2", "options": ["花岗岩", "灰岩", "砂岩"] },
    { "op": "delete_field", "id": "f1a8z0" }
  ]
}
```

- 只能在线做。服务端的 `schema_version` 不等于 `base_version` 时返回 409 `stale`，带上当前结构；客户端更新本地结构后，让用户在新结构上重做。
- 一次请求里的操作按顺序执行，要么全部成功，要么一个都不做。成功后 `schema_version` 加 1，响应带新的结构。
- 字段类型、`geometry_type` 和 `crs` 都不能改。要换字段类型，就新增一个字段、迁移数据、再删掉旧字段。
- 删除字段：行里不再返回这个字段，旧值留在服务端的历史里；之后对它的修改进冲突记录（3.4 规则 4）。
- 谁能改结构由权限决定，权限一节待写（[ADR 0009](../../docs/adr/0009-roles-and-permissions.md)）。

### 4.4 离线的客户端

- 离线时只能改数据和 4.1 里按字段合并的属性，不能改结构。
- 客户端按它知道的结构提交，服务端按当前结构合并：字段改名不影响；客户端不知道的新字段，它自然不会提交；已删除字段上的修改进冲突记录。
- 客户端拉取到更高的 `schema_version` 时，更新本地结构。
