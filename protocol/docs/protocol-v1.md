# 同勘 GeoCrew 协同协议 v1（草案）

> 状态：草案，M2 期间逐节写，M3 实现。依据 [ADR 0008](../../docs/adr/0008-sync-and-merge.md)（同步与合并）和 [ADR 0009](../../docs/adr/0009-roles-and-permissions.md)（身份与权限）。v1 不兼容 v0，v0 的客户端不再支持；[v0 文档](protocol-v0.md)在 v1 写完之前只作参考。v1 的接口在 M3 实现时一并写进 [`openapi.yaml`](openapi.yaml)；在那之前，`openapi.yaml` 描述的仍是现行的 v0。

## 1. 和 v0 的主要区别

- 以图层为中心：数据都是图层里的"行"，每行带全局 UUID，字段用稳定的字段 ID 作键，改名不影响合并。
- 按字段合并：客户端只提交改过的字段，服务端按字段做三方合并；落败的值写进冲突记录，不再整条覆盖。
- 编辑时间换算到服务端时钟，手机时钟不准不会影响谁胜出。

## 3. 行与合并

### 3.1 行

- 每行属于一个图层，有全局唯一的 UUID，由创建它的客户端生成。
- 字段的键是图层结构里的字段 ID，不是字段名。几何是一个名为 `geom` 的字段，值是 GeoJSON 几何对象，坐标用图层的坐标系；几何整体算一个字段。
- 服务端为每个字段记四样东西：值、最后修改人、编辑时间（换算到服务端时钟，见 3.3）、最后修改它的序号 `seq`。
- 删除也按字段记：`deleted` 的值为 `true` 或 `false`。删除的行保留全部字段（墓碑），可以恢复。

### 3.2 提交一条修改

客户端每次只提交自上次同步以来改过的字段：

```json
{
  "row": "8d3c6f0e-0c1a-4d7e-9a43-3f1d9b0f4e21",
  "base_seq": 5,
  "client_now": "2026-11-25T12:00:00Z",
  "set": {
    "f1": { "value": "D001", "edited_at": "2026-11-25T11:50:00Z" },
    "geom": { "value": { "type": "Point", "coordinates": [114.0, 30.0] }, "edited_at": "2026-11-25T11:50:00Z" }
  },
  "delete": { "value": true, "edited_at": "2026-11-25T11:55:00Z" }
}
```

| 字段 | 说明 |
|---|---|
| `base_seq` | 客户端最后一次看到这一行时，服务端的序号；新建的行为 `0` |
| `client_now` | 发出请求时客户端的时钟；批量提交时写在请求顶层，对其中所有修改有效（5.1） |
| `set` | 改过的字段，各带新值和客户端记下的编辑时间；没改的字段不要带 |
| `delete` | 可选。`true` 删除，`false` 恢复；值不是布尔值的请求被拒绝 |

修改人由服务端按鉴权身份填写，不由客户端提供。批量提交的请求和响应见 5.1。

### 3.3 编辑时间

服务端把客户端的编辑时间换算到自己的时钟：

> 编辑时间（服务端）= 服务端收到请求的时间 −（`client_now` − `edited_at`）

换算结果晚于服务端当前时间的，按服务端当前时间算。

### 3.4 合并规则

服务端逐个字段处理 `set` 里的修改。字段的 `seq` 大于 `base_seq`，说明客户端修改之后别人也改过它，称为"并发修改"。

1. **没有并发修改**（服务端还没有这个字段，或它的 `seq` 不大于 `base_seq`）：直接采用新值。
2. **有并发修改，值相同**：不变，不算冲突。值按 JSON 比较，忽略格式和对象键的顺序。
3. **有并发修改，值不同**：编辑时间晚的为准；时间相同的，后到达服务端的为准。落败的值写进冲突记录（`value`）。
4. **字段已从图层删除**：这次修改写进冲突记录（`deleted_field`），其余字段照常处理。

删除和恢复：

5. **删除**：`base_seq` 之后没有任何字段被改过，才删除；否则不删，删除写进冲突记录（`delete_rejected`），提示删除的人。
6. **别人删除了这一行**（删除发生在 `base_seq` 之后），而这次修改改了字段：字段照常合并，这一行恢复，那次删除写进冲突记录（`delete_overridden`），提示删除的人。恢复记在这次修改名下：修改人是提交者，时间是服务端收到请求的时间，序号是这次修改的序号。
7. **恢复**：已删除的行，`delete` 为 `false` 时恢复。

### 3.5 冲突记录

```json
{ "kind": "value", "field": "f1",
  "kept": { "value": "from m2", "by": "m2", "at": "2026-11-25T11:30:00Z", "seq": 9 },
  "lost": { "value": "from m1", "by": "m1", "at": "2026-11-25T11:00:00Z", "seq": 7 } }
```

| `kind` | 什么时候 | `lost` 是 |
|---|---|---|
| `value` | 规则 3 | 落败的值（可能是服务端原来的值，也可能是这次提交的值） |
| `deleted_field` | 规则 4 | 这次提交的值 |
| `delete_rejected` | 规则 5 | 这次提交的删除 |
| `delete_overridden` | 规则 6 | 别人的那次删除 |

- 一次修改产生的冲突，先按字段 ID 排序列出字段冲突，再列删除冲突。
- 有未处理冲突的行标为"有冲突"。组长或当事人可以一键换成另一个值；换值就是一次普通修改，按同样的规则合并。

### 3.6 共用测试样例

合并规则的测试样例在 [`protocol/testdata/merge/cases.json`](../testdata/merge/cases.json)，服务端（`server/internal/merge`）和安卓客户端都必须逐条通过。每条样例给出服务端当前的行、一次修改和期望的结果；服务端当前时间、序号和图层现有字段取文件开头的默认值，个别样例另行指定。

服务端另有随机交错测试：几个时钟不准的客户端交替离线修改、删除、恢复和提交，检查任何一次提交的值要么进了行，要么进了冲突记录。

## 4. 图层与结构变更

### 4.1 图层

图层本身也是一行，属于系统表 `layers`，有全局唯一的 UUID。它的属性分两类：

- **按第 3 节合并的字段**：`name`（名称）、`style`（样式，JSON，见 [ADR 0006](../../docs/adr/0006-rendering-and-styles.md)）、`form`（表单布局，JSON）、`order`（图层顺序，数字）。可以离线改，和普通行的字段一样合并。`style` 和 `form` 各自整体算一个字段：两人同时改了样式的不同部分，也按同一字段处理，落败的那份进冲突记录。
- **结构**：几何类型 `geometry_type`、坐标系 `crs`、字段定义 `fields` 和结构版本 `schema_version`。只能在线改，见 4.3。

| 结构 | 说明 |
|---|---|
| `geometry_type` | `Point`、`LineString`、`Polygon`、`MultiPoint`、`MultiLineString`、`MultiPolygon`，或 `None`（没有几何的表）。创建后不能改 |
| `crs` | 创建时定，`EPSG:代码` 或 WKT2 文本；创建后不能改，要换坐标系就新建图层再导入。几何坐标按这个坐标系，轴顺序一律东、北（经度、纬度） |
| `fields` | 字段定义的列表，见 4.2 |
| `schema_version` | 结构版本，从 1 开始，每次结构变更加 1 |

共享工作区里的图层要在线创建：创建请求带上初始结构，`schema_version` 为 1。离线时只能在本地工程里建图层，本地工程加入工作区时再上传（工作区一节待写）。

### 4.2 字段

```json
{ "id": "f3k9x2", "name": "岩性", "type": "string", "options": ["花岗岩", "灰岩"] }
```

| 属性 | 说明 |
|---|---|
| `id` | 由新增字段的一方生成，1 至 64 个字符（字母、数字、`_`、`-`），在图层内唯一，删除后也不再使用。行里的字段用它作键（第 3 节）。`geom` 留给几何，不能用 |
| `name` | 显示名，可以改；改名不影响已有数据，也不影响合并 |
| `type` | 见下表；创建后不能改 |
| `options` | 可选。取值列表，界面上显示成选择框 |

| `type` | JSON 中的值 |
|---|---|
| `string` | 字符串 |
| `integer` | 整数，范围 ±(2^53 − 1)：超出这个范围时很多 JSON 解析器会丢精度，更大的编号请用 `string` |
| `real` | 数字 |
| `boolean` | `true` 或 `false` |
| `date` | 字符串，`2026-11-25` |
| `datetime` | 字符串，RFC 3339，例如 `2026-11-25T11:50:00Z` |
| `json` | 任意 JSON 值 |

任何类型的值都可以是 `null`，表示没有填。

### 4.3 结构变更

```
POST /api/v1/workspaces/{ws}/layers/{layer}/schema
```

```json
{
  "base_version": 3,
  "ops": [
    { "op": "add_field", "field": { "id": "f7q2m1", "name": "采样编号", "type": "string" } },
    { "op": "rename_field", "id": "f3k9x2", "name": "岩石名称" },
    { "op": "set_options", "id": "f3k9x2", "options": ["花岗岩", "灰岩", "砂岩"] },
    { "op": "delete_field", "id": "f1a8z0" }
  ]
}
```

- 只能在线做。服务端的 `schema_version` 不等于 `base_version` 时返回 409 `stale`，带上当前结构；客户端更新本地结构后，让用户在新结构上重做。
- 一次请求里的操作按顺序执行，要么全部成功，要么一个都不做。成功后 `schema_version` 加 1，响应带新的结构。
- 字段类型、`geometry_type` 和 `crs` 都不能改。要换字段类型，就新增一个字段、迁移数据、再删掉旧字段。
- 删除字段：行里不再返回这个字段，旧值留在服务端的历史里；之后对它的修改进冲突记录（3.4 规则 4）。
- 改结构需要 `edit_schema` 权限，见第 6 节。

### 4.4 离线的客户端

- 离线时只能改数据和 4.1 里按字段合并的属性，不能改结构。
- 客户端按它知道的结构提交，服务端按当前结构合并：字段改名不影响；客户端不知道的新字段，它自然不会提交；已删除字段上的修改进冲突记录。
- 客户端拉取到更高的 `schema_version` 时，更新本地结构。

## 5. 提交、拉取与冲突处理

### 5.1 提交

```
POST /api/v1/workspaces/{ws}/rows
```

```json
{
  "client_now": "2026-11-25T12:00:00Z",
  "changes": [
    { "id": "c2b1…", "layer": "4f0e…", "row": "8d3c…", "base_seq": 5,
      "set": { "f1": { "value": "D001", "edited_at": "2026-11-25T11:50:00Z" } } }
  ]
}
```

- 每条修改就是 3.2 的格式，再加上客户端生成的修改 ID `id`（UUID）和所在图层 `layer`。`client_now` 写在请求里，对其中所有修改有效。
- 单次最多 `max_push_batch` 条（见 7.3），同一请求里同一行只能出现一次。
- 服务端在一个事务里逐条处理，每条接受的修改分配一个新的 `seq`。响应和请求一一对应：

```json
{
  "results": [
    { "id": "c2b1…", "status": "applied", "seq": 18, "conflicts": [] },
    { "id": "77ab…", "status": "duplicate", "seq": 12 },
    { "id": "5e10…", "status": "rejected", "error": "invalid_value", "message": "f2 must be an integer" }
  ],
  "seq": 18
}
```

| `status` | 含义 | 客户端处理 |
|---|---|---|
| `applied` | 已按第 3 节合并，`conflicts` 列出这次产生的冲突（可能为空） | 标为已同步；有冲突就提示用户 |
| `duplicate` | 这个修改 ID 已经处理过（重试），返回当时的 `seq`。修改 ID 和修改历史保存一样久，客户端不能重复使用 | 标为已同步 |
| `rejected` | 格式或权限不对，这条修改没有生效；`error` 是机器码 | 留在本地，提示用户 |

`rejected` 的机器码：`unknown_layer`（图层不存在）、`invalid_value`（值和字段类型不符，或 `delete` 不是布尔值）、`forbidden`（没有权限）、`archived`（工作区已归档）。不在这里的问题（请求本身格式不对、批次过大）按整个请求出错，返回相应的状态码。

### 5.2 拉取

```
GET /api/v1/workspaces/{ws}/changes?since=17&limit=500
```

返回 `seq > since` 的变化，按 `seq` 升序：

```json
{
  "layers": [ { "id": "4f0e…", "schema_version": 4, "fields": [ … ], "name": { "value": "地质点", "by": "m1", "at": "…", "seq": 20 } } ],
  "rows": [
    { "layer": "4f0e…", "id": "8d3c…", "conflicted": true,
      "fields": { "f1": { "value": "D001", "by": "m2", "at": "2026-11-25T11:50:00Z", "seq": 18 } },
      "deleted": null }
  ],
  "conflicts": [
    { "id": "k91…", "layer": "4f0e…", "row": "8d3c…", "seq": 18, "resolved": false,
      "kind": "value", "field": "f1", "kept": { … }, "lost": { … } }
  ],
  "seq": 25,
  "more": false
}
```

- 行和图层都返回当前的完整状态，每个字段带 3.1 的四项信息；一行多次修改只返回最新状态。已删除的行也返回，带 `deleted`。
- `seq` 是下次请求应传的 `since`；`more` 为 `true` 时立即继续拉取。
- 客户端为每一行记下拉到它时的 `seq`，下次修改这一行就用它作 `base_seq`。这样在它之后别人改过的字段，`seq` 一定更大，服务端能认出是并发修改。
- `base_seq` 只在拉取到这一行的新状态时更新，不能用提交返回的 `seq`：那之前别人可能改过客户端还没拉到的字段，用提交的 `seq` 作基准，这些修改就不再算并发，会被悄悄覆盖。
- `conflicts` 包括新产生的冲突，也包括状态变了（比如被处理了）的冲突。

### 5.3 处理冲突

```
POST /api/v1/workspaces/{ws}/conflicts/{id}/resolve
{ "choose": "lost" }
```

- `choose` 是 `kept`（保留现在的值，只把冲突标为已处理）或 `lost`（换成落败的那个值）。
- 选 `lost` 时，服务端以处理人的名义做一次普通修改，以冲突产生时的 `seq` 作 `base_seq`，按第 3 节合并；这期间如果字段又被别人改过，就会产生新的冲突，不会悄悄覆盖。
- 冲突处理完后，所在行没有其他未处理冲突时，`conflicted` 变为 `false`。
- 谁能处理冲突：组长，以及冲突两边的当事人。这不是一项可以分配的权限：除这三方之外，谁也不能替别人选（第 6 节）。

### 5.4 推荐的客户端同步流程

1. 本地每次修改：记下改了哪个字段、新值和编辑时间，标为"待上传"；同一字段多次修改只保留最后一次。
2. 先上传修改引用的附件（附件一节待写），再分批提交待上传的修改，每条带上这一行的 `base_seq` 和一个修改 ID；重试时用同一个修改 ID。
3. 从上次保存的 `seq` 开始拉取，直到 `more` 为 `false`，用服务端的状态更新本地；本地仍有待上传修改的字段，保留本地的值。
4. 保存最新的 `seq`，有新冲突就提示用户。

## 6. 工作区、成员与权限

本节先写权限的规则（[ADR 0009](../../docs/adr/0009-roles-and-permissions.md)），成员和身份的管理接口待写。

### 6.1 身份

- **组长**：每个工作区只有一位，拥有全部权限，不受任何设置限制，可以转让。组长丢了手机时，由服务端管理员用命令行转给别人。
- **组员**（`member`）：每个成员都有的基础身份，组长可以改它的权限。
- **自定义身份**：组长或有"管理身份"权限的人可以新建，比如副组长、采样员、访客。一个人可以有多个身份。
- 每个身份有一个位置 `position`，数字大的排在上面。组员的位置是 0。

### 6.2 权限清单

| 分组 | 权限 |
|---|---|
| 工作组 | `manage_members` 管理成员、`manage_roles` 管理身份、`manage_workspace` 修改工作组（改名、归档）、`manage_settings` 修改共享设置、`post_announcements` 发公告 |
| 图层 | `manage_layers` 新建和删除共享图层、`edit_schema` 修改结构和样式、`edit_rows` 编辑要素、`delete_rows` 删除要素、`review` 审核、`assign_tasks` 指派任务 |
| 交流 | `send_messages` 发消息、`start_rollcall` 发起点名、`delete_messages` 删除别人的消息 |
| 位置 | `view_locations` 查看组员位置 |
| 数据 | `export_data` 导出和下载整组数据、`create_view_links` 生成网页查看链接、`create_ai_links` 生成 AI 读写链接 |
| 插件 | `manage_plugins` 安装和启用插件 |

- `edit_rows` 和 `delete_rows` 有三档：`none`、`own`（只限自己建的行）、`all`；其余权限只有开和关，只接受 `true` / `false`，保存身份时服务端拒绝别的值。没写的就是关。
- `view_layer` 只能按图层设置（6.4）：没有覆盖时，每个人都能看到每个图层。
- **安全权利**不在清单里，任何设置都关不掉：发紧急求助、回应点名、报外出和返回、退出工作组、开关自己的位置共享。

### 6.3 计算规则

成员在全局的权限，是他所有身份（包括组员）的权限合在一起：开关类只要有一个身份开了就算开；分档的取最高一档。组长永远拥有全部权限。

### 6.4 图层覆盖

每个图层可以为某些身份单独设置 `view_layer`、`edit_rows`、`delete_rows`。算某人在某个图层上的权限时，按 Discord 的规则：

1. 先取他在全局的权限（6.3）。
2. 组员身份在这个图层上有覆盖的，用覆盖的值替换。
3. 他的其他身份里，有在这个图层上覆盖了同一项的，取这些覆盖里最高的一档替换。没有覆盖的身份，不参与这一步。

所以组员身份上的覆盖对所有人都生效，包括副组长：要让某个身份例外，就在那个身份上也设覆盖。某人有采样员（全局可编辑全部）和访客（这个图层上不能编辑）两个身份时，访客的覆盖会把他在这个图层上的编辑权去掉。组长不受图层覆盖限制。

能看到一个图层（`view_layer`），才能编辑或删除它的行。`own` 表示只能动自己建的行，行的创建人是第一次提交这一行的成员。新建行需要 `edit_rows` 至少为 `own`，新行算作创建人自己的行。

### 6.5 上下顺序

- 成员的级别是他身份里最高的位置；组长高于所有人。
- 有 `manage_roles` 的人，只能修改、删除排在自己最高身份下面的身份；给身份授权时，只能授出自己拥有的权限，分档的不能高于自己那一档。
- 有 `manage_members` 的人，只能把排在自己下面的身份分给别人，只能调整或移出级别比自己低的成员。
- 任何人都不能管理组长，也不能用这些权限管理自己。

### 6.6 离线时被拒的修改

离线时做的修改，联网后如果因为权限变了被拒绝（5.1 的 `forbidden`），就留在手机上，标为"未能提交"，不删除。

### 6.7 共用测试样例

权限规则的测试样例在 [`protocol/testdata/permissions/cases.json`](../testdata/permissions/cases.json)：一个设好身份、成员和图层覆盖的工作区，加上一组提问和答案。服务端（`server/internal/perm`）和安卓客户端都必须逐条通过；客户端离线时用同一套规则自己判断。

## 7. 基本约定

章节按写作顺序编号，v1 写完时再整理顺序。

### 7.1 传输与格式

- **传输**：HTTPS + JSON（UTF-8），接口路径以 `/api/v1` 开头；实时通道用 WebSocket（`wss://`）。证书见 7.4 和 [ADR 0014](../../docs/adr/0014-certificates.md)。
- **时间**：RFC 3339 的 UTC 字符串，例如 `2026-11-25T12:00:00Z`，可以带小数秒。
- **标识**：
  - 行、图层、修改 ID 由客户端生成 UUID，写成小写、带连字符的 36 位文本。离线也能生成，不会重复。
  - 工作区、成员、身份、冲突的 ID 由服务端生成，是 1–64 位的字母、数字、`-` 或 `_`，客户端只能原样使用，不要解析。
- **几何**：GeoJSON 几何对象，坐标按图层的坐标系，轴顺序一律东、北，见 3.1 和 4.1。
- **兼容**：
  - 双方都必须忽略不认识的 JSON 字段、不认识的实时消息类型和不认识的能力名。
  - 不认识的错误码，按 HTTP 状态码处理。

### 7.2 错误格式

出错时，响应体是：

```json
{ "error": "forbidden", "message": "edit_rows is required", "permission": "edit_rows" }
```

`error` 是稳定的机器码，客户端按它处理；`message` 只给人看，不保证措辞。个别错误带额外的键，表里写明。

| 状态码 | 机器码 | 含义 |
|---|---|---|
| 400 | `bad_json` | 请求体不是合法的 JSON |
| 400 | `invalid` | 缺参数，或参数的格式、取值不对 |
| 401 | `unauthorized` | 令牌缺失、错误或已被吊销 |
| 403 | `forbidden` | 没有权限；`permission` 写明缺哪一项（第 6 节） |
| 404 | `not_found` | 资源不存在，或无权知道它存在 |
| 404 | `bad_invite` | 邀请码不存在或已经重置 |
| 409 | `stale` | 基于旧版本修改，比如结构变更（4.3）；带上当前状态的键在各节写明 |
| 409 | `archived` | 工作区已归档，不能修改 |
| 413 | `batch_too_large` | 一次提交的条数超过 `max_push_batch` |
| 413 | `too_large` | 请求体或文件超过上限 |
| 429 | `rate_limited` | 请求太频繁；`Retry-After` 头写明多少秒后再试 |

提交里单条修改被拒，不按整个请求出错，见 5.1。

### 7.3 服务端信息与能力

```
GET /api/v1/info
```

不需要令牌，客户端添加服务器和检查更新时调用：

```json
{
  "protocol": 1,
  "server": "geocrew-server",
  "version": "0.3.0",
  "capabilities": ["sync", "files", "realtime", "gdal"],
  "limits": { "max_push_batch": 500, "max_pull_batch": 1000, "max_file_size": 1073741824 }
}
```

- `protocol` 是协议的大版本，v1 为 `1`。客户端遇到自己不支持的大版本，提示用户升级应用或服务端，不要接着请求。
- `version` 是服务端的版本号，比较规则见 [releases.md](releases.md)。
- `limits`：`max_push_batch` 是一次最多提交几条修改（5.1）；`max_pull_batch` 是拉取时 `limit` 的上限，超过的按上限处理（5.2）；`max_file_size` 是单个附件的字节数上限。

客户端只在服务端声明了某项能力时才打开对应的功能，没声明就隐藏，或者提示"服务器不支持"，不要靠请求失败来判断。自己写服务端的，可以只做核心部分，再一项项往上加。

| 能力 | 含义 |
|---|---|
| `sync` | 行同步、合并和冲突处理（第 3–5 节），以及成员与权限（第 6 节）。核心能力，必须有 |
| `create` | 接受新建工作区。运维可以关掉，只留管理员用命令行创建 |
| `files` | 附件（待写） |
| `realtime` | 实时通道（待写） |
| `gdal` | 服务端带 GDAL 辅助程序（[ADR 0013](../../docs/adr/0013-server-gdal-helper.md)），可以做坐标转换和多格式导出。某个平台上辅助程序不可用时，服务端不声明这一项，依赖它的功能隐藏 |

其余能力随对应的章节补上。

### 7.4 加入与鉴权

**创建工作区**（需要 `create` 能力）：

```
POST /api/v1/workspaces
{ "name": "2026 秋季填图", "nickname": "张三", "device": "Galaxy S24" }
```

返回 `{workspace, member, token}`：新工作区、组长自己的成员信息和令牌。创建人就是组长。服务端没有声明 `create` 时返回 `403 forbidden`。

**加入**：

```
POST /api/v1/join
{ "invite_code": "K7QX2MPA", "nickname": "李四", "device": "Mate 60" }
```

返回同样的 `{workspace, member, token}`，新成员只有组员身份。邀请码 8 位，不区分大小写，不含容易混淆的 0、O、1、I；有 `manage_members` 权限的人可以重置，旧码立即失效。

**令牌**：

- 之后的请求在头部带 `Authorization: Bearer <令牌>`。
- 令牌只在创建、加入时返回一次，服务端只存哈希。
- 每台设备一枚令牌，`device` 是给人看的设备名。
- 用邀请码加入，每次都是一个新成员。同一个人换手机，要保留身份和自己建的行，不能重新加入，而要给原来的成员添一台设备：在旧手机上生成一次性的转移码，或者由有 `manage_members` 权限的人生成（接口在成员一节里写）。
- 每台设备的令牌可以单独吊销，本人和有 `manage_members` 权限的人都可以操作，丢了手机时用。
- 成员被移出工作区时，他的所有令牌立即失效，实时连接断开。

**邀请二维码**：

```
geocrew://join?server=<URL 编码的根地址>&code=<邀请码>&pin=<公钥指纹>
```

- `pin` 是服务端证书公钥（SubjectPublicKeyInfo，DER 编码）的 SHA-256，写成不带填充的 base64url，见 [ADR 0014](../../docs/adr/0014-certificates.md)。
- 带 `pin` 时，`server` 必须是 `https://` 地址，否则客户端拒绝。客户端只认公钥和它一致的证书，不看证书链、有效期和主机名，所以证书续期、IP 变了都不用重新邀请。客户端把指纹和服务器地址存在一起，之后每次连接都这样检查。
- 服务端换了密钥（比如换机器时没带上原来的密钥），带指纹的客户端都会连不上。客户端要明确提示"服务器的密钥变了"，让用户扫新的邀请码，或者和组长核对新指纹后再更新，不能自动接受。
- 不带 `pin` 时（服务端用的是正式证书），按系统的证书机构正常校验。
- 手动输入服务器地址加入的，客户端显示证书的公钥指纹，让用户和组长核对后再保存。组长在工作区页能看到指纹，服务端启动时也会打印出来。
