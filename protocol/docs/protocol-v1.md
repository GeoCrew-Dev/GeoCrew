# 同勘 GeoCrew 协同协议 v1（草案）

> 状态：草案，M2 期间逐节写，M3 实现。依据 [ADR 0008](../../docs/adr/0008-sync-and-merge.md)（同步与合并）和 [ADR 0009](../../docs/adr/0009-roles-and-permissions.md)（身份与权限）。v1 不兼容 v0，v0 的客户端不再支持；[v0 文档](protocol-v0.md)在 v1 写完之前只作参考。v1 的接口在 M3 实现时一并写进 [`openapi.yaml`](openapi.yaml)；在那之前，`openapi.yaml` 描述的仍是现行的 v0。

## 1. 和 v0 的主要区别

- 以图层为中心：数据都是图层里的"行"，每行带全局 UUID，字段用稳定的字段 ID 作键，改名不影响合并。
- 按字段合并：客户端只提交改过的字段，服务端按字段做三方合并；落败的值写进冲突记录，不再整条覆盖。
- 编辑时间换算到服务端时钟，手机时钟不准不会影响谁胜出。

## 3. 基本约定

### 3.1 传输与格式

- **传输**：HTTPS + JSON（UTF-8），接口路径以 `/api/v1` 开头；实时通道用 WebSocket（`wss://`）。证书见 3.4 和 [ADR 0014](../../docs/adr/0014-certificates.md)。
- **时间**：RFC 3339 的 UTC 字符串，例如 `2026-11-25T12:00:00Z`，可以带小数秒。
- **标识**：
  - 行、图层、修改 ID 由客户端生成 UUID，写成小写、带连字符的 36 位文本。离线也能生成，不会重复。
  - 工作区、成员、身份、冲突的 ID 由服务端生成，是 1–64 位的字母、数字、`-` 或 `_`，客户端只能原样使用，不要解析。
- **几何**：GeoJSON 几何对象，坐标按图层的坐标系，轴顺序一律东、北，见 6.1 和 7.1。
- **兼容**：
  - 双方都必须忽略不认识的 JSON 字段、不认识的实时消息类型和不认识的能力名。
  - 不认识的错误码，按 HTTP 状态码处理。

### 3.2 错误格式

出错时，响应体是：

```json
{ "error": "forbidden", "message": "edit_rows is required", "permission": "edit_rows" }
```

`error` 是稳定的机器码，客户端按它处理；`message` 只给人看，不保证措辞。个别错误带额外的键，表里写明。

| 状态码 | 机器码 | 含义 |
|---|---|---|
| 400 | `bad_json` | 请求体不是合法的 JSON |
| 400 | `invalid` | 缺参数，或参数的格式、取值不对 |
| 400 | `hash_mismatch` | 上传的文件和声明的哈希对不上（9.2） |
| 401 | `unauthorized` | 令牌缺失、错误或已被吊销 |
| 403 | `forbidden` | 没有权限；`permission` 写明缺哪一项（第 4 节） |
| 404 | `not_found` | 资源不存在，或无权知道它存在 |
| 404 | `bad_invite` | 邀请码不存在或已经重置 |
| 404 | `not_uploaded` | 附件行引用的文件还没传上来（9.3） |
| 409 | `stale` | 基于旧版本修改，比如结构变更（7.3）；带上当前状态的键在各节写明 |
| 409 | `archived` | 工作区已归档，不能修改 |
| 409 | `offset_mismatch` | 分块上传的位置不对；`offset` 写明服务端已经收到多少字节（9.2） |
| 413 | `batch_too_large` | 一次提交的条数超过 `max_push_batch` |
| 413 | `too_large` | 请求体或文件超过上限 |
| 429 | `rate_limited` | 请求太频繁；`Retry-After` 头写明多少秒后再试 |

提交里单条修改被拒，不按整个请求出错，见 8.1。

### 3.3 服务端信息与能力

```
GET /api/v1/info
```

不需要令牌，客户端添加服务器和检查更新时调用：

```json
{
  "protocol": 1,
  "server": "geocrew-server",
  "version": "0.3.0",
  "capabilities": ["sync", "files", "realtime", "gdal"],
  "limits": { "max_push_batch": 500, "max_pull_batch": 1000, "max_file_size": 1073741824 }
}
```

- `protocol` 是协议的大版本，v1 为 `1`。客户端遇到自己不支持的大版本，提示用户升级应用或服务端，不要接着请求。
- `version` 是服务端的版本号，比较规则见 [releases.md](releases.md)。
- `limits`：`max_push_batch` 是一次最多提交几条修改（8.1）；`max_pull_batch` 是拉取时 `limit` 的上限，超过的按上限处理（8.2）；`max_file_size` 是单个附件的字节数上限。

客户端只在服务端声明了某项能力时才打开对应的功能，没声明就隐藏，或者提示"服务器不支持"，不要靠请求失败来判断。自己写服务端的，可以只做核心部分，再一项项往上加。

| 能力 | 含义 |
|---|---|
| `sync` | 行同步、合并和冲突处理（第 6–8 节），以及成员与权限（第 4 节）。核心能力，必须有 |
| `create` | 接受新建工作区。运维可以关掉，只留管理员用命令行创建 |
| `files` | 附件（第 9 节） |
| `realtime` | 实时通道（第 10 节） |
| `gdal` | 服务端带 GDAL 辅助程序（[ADR 0013](../../docs/adr/0013-server-gdal-helper.md)），可以做坐标转换和多格式导出。某个平台上辅助程序不可用时，服务端不声明这一项，依赖它的功能隐藏 |

其余能力随对应的章节补上。

### 3.4 加入与鉴权

**创建工作区**（需要 `create` 能力）：

```
POST /api/v1/workspaces
{ "name": "2026 秋季填图", "nickname": "张三", "device": "Galaxy S24" }
```

返回 `{workspace, member, token}`：新工作区、组长自己的成员信息和令牌。创建人就是组长。服务端没有声明 `create` 时返回 `403 forbidden`。

**加入**：

```
POST /api/v1/join
{ "invite_code": "K7QX2MPA", "nickname": "李四", "device": "Mate 60" }
```

返回同样的 `{workspace, member, token}`，新成员只有组员身份。邀请码 8 位，不区分大小写，不含容易混淆的 0、O、1、I；有 `manage_members` 权限的人可以重置，旧码立即失效。

**令牌**：

- 之后的请求在头部带 `Authorization: Bearer <令牌>`。
- 令牌只在创建、加入时返回一次，服务端只存哈希。
- 每台设备一枚令牌，`device` 是给人看的设备名。
- 用邀请码加入，每次都是一个新成员。同一个人换手机，要保留身份和自己建的行，不能重新加入，而要给原来的成员添一台设备：在旧手机上生成一次性的转移码，或者由有 `manage_members` 权限的人生成（接口在成员一节里写）。
- 每台设备的令牌可以单独吊销，本人和有 `manage_members` 权限的人都可以操作，丢了手机时用。
- 成员被移出工作区时，他的所有令牌立即失效，实时连接断开。

**邀请二维码**：

```
geocrew://join?server=<URL 编码的根地址>&code=<邀请码>&pin=<公钥指纹>
```

- `pin` 是服务端证书公钥（SubjectPublicKeyInfo，DER 编码）的 SHA-256，写成不带填充的 base64url，见 [ADR 0014](../../docs/adr/0014-certificates.md)。
- 带 `pin` 时，`server` 必须是 `https://` 地址，否则客户端拒绝。客户端只认公钥和它一致的证书，不看证书链、有效期和主机名，所以证书续期、IP 变了都不用重新邀请。客户端把指纹和服务器地址存在一起，之后每次连接都这样检查。
- 服务端换了密钥（比如换机器时没带上原来的密钥），带指纹的客户端都会连不上。客户端要明确提示"服务器的密钥变了"，让用户扫新的邀请码，或者和组长核对新指纹后再更新，不能自动接受。
- 不带 `pin` 时（服务端用的是正式证书），按系统的证书机构正常校验。
- 手动输入服务器地址加入的，客户端显示证书的公钥指纹，让用户和组长核对后再保存。组长在工作区页能看到指纹，服务端启动时也会打印出来。

## 4. 工作区、成员与权限

本节写权限的规则（[ADR 0009](../../docs/adr/0009-roles-and-permissions.md)），接口见第 5 节。

### 4.1 身份

- **组长**：每个工作区只有一位，拥有全部权限，不受任何设置限制，可以转让。组长丢了手机时，由服务端管理员用命令行转给别人。
- **组员**（`member`）：每个成员都有的基础身份，组长可以改它的权限。新工作区里，组员默认有这些权限，大致相当于 v0 的组员：`edit_rows` 和 `delete_rows` 为 `all`，以及 `assign_tasks`、`send_messages`、`view_locations`、`export_data`、`create_view_links`、`create_ai_links`。
- **自定义身份**：组长或有"管理身份"权限的人可以新建，比如副组长、采样员、访客。一个人可以有多个身份。
- 每个身份有一个位置 `position`，数字大的排在上面。组员的位置是 0。

### 4.2 权限清单

| 分组 | 权限 |
|---|---|
| 工作组 | `manage_members` 管理成员、`manage_roles` 管理身份、`manage_workspace` 修改工作组（改名、归档）、`manage_settings` 修改共享设置、`post_announcements` 发公告 |
| 图层 | `manage_layers` 新建和删除共享图层、`edit_schema` 修改结构和样式、`edit_rows` 编辑要素、`delete_rows` 删除要素、`review` 审核、`assign_tasks` 指派任务 |
| 交流 | `send_messages` 发消息、`start_rollcall` 发起点名、`delete_messages` 删除别人的消息 |
| 位置 | `view_locations` 查看组员位置 |
| 数据 | `export_data` 导出和下载整组数据、`create_view_links` 生成网页查看链接、`create_ai_links` 生成 AI 读写链接 |
| 插件 | `manage_plugins` 安装和启用插件 |

- `edit_rows` 和 `delete_rows` 有三档：`none`、`own`（只限自己建的行）、`all`；其余权限只有开和关，只接受 `true` / `false`，保存身份时服务端拒绝别的值。没写的就是关。
- `view_layer` 只能按图层设置（4.4）：没有覆盖时，每个人都能看到每个图层。
- **安全权利**不在清单里，任何设置都关不掉：发紧急求助、回应点名、报外出和返回、退出工作组、开关自己的位置共享。

### 4.3 计算规则

成员在全局的权限，是他所有身份（包括组员）的权限合在一起：开关类只要有一个身份开了就算开；分档的取最高一档。组长永远拥有全部权限。

### 4.4 图层覆盖

每个图层可以为某些身份单独设置 `view_layer`、`edit_rows`、`delete_rows`。算某人在某个图层上的权限时，按 Discord 的规则：

1. 先取他在全局的权限（4.3）。
2. 组员身份在这个图层上有覆盖的，用覆盖的值替换。
3. 他的其他身份里，有在这个图层上覆盖了同一项的，取这些覆盖里最高的一档替换。没有覆盖的身份，不参与这一步。

所以组员身份上的覆盖对所有人都生效，包括副组长：要让某个身份例外，就在那个身份上也设覆盖。某人有采样员（全局可编辑全部）和访客（这个图层上不能编辑）两个身份时，访客的覆盖会把他在这个图层上的编辑权去掉。组长不受图层覆盖限制。

能看到一个图层（`view_layer`），才能编辑或删除它的行。`own` 表示只能动自己建的行，行的创建人是第一次提交这一行的成员。新建行需要 `edit_rows` 至少为 `own`，新行算作创建人自己的行。

### 4.5 上下顺序

- 成员的级别是他身份里最高的位置；组长高于所有人。
- 有 `manage_roles` 的人，只能修改、删除排在自己最高身份下面的身份；给身份授权时，只能授出自己拥有的权限，分档的不能高于自己那一档。
- 有 `manage_members` 的人，只能把排在自己下面的身份分给别人，只能调整或移出级别比自己低的成员。
- 任何人都不能管理组长，也不能用这些权限管理自己。

### 4.6 离线时被拒的修改

离线时做的修改，联网后如果因为权限变了被拒绝（8.1 的 `forbidden`），就留在手机上，标为"未能提交"，不删除。

### 4.7 共用测试样例

权限规则的测试样例在 [`protocol/testdata/permissions/cases.json`](../testdata/permissions/cases.json)：一个设好身份、成员和图层覆盖的工作区，加上一组提问和答案。服务端（`server/internal/perm`）和安卓客户端都必须逐条通过；客户端离线时用同一套规则自己判断。

## 5. 工作区、成员与身份的接口

第 4 节的规则落到接口上。下面以 `/api/` 开头的是完整路径，其余的都省略了前缀 `/api/v1/workspaces/{ws}`。每个接口要的权限写在后面；不满足时返回 `403 forbidden`（3.2）。

### 5.1 工作区

- `GET /api/v1/workspaces/{ws}`：工作区信息 `{id, name, archived_at?, leader, fingerprint, invite_code?, access_version}`。
  - `fingerprint` 是服务端证书的公钥指纹（3.4），组长核对用。
  - `invite_code` 只返回给有 `manage_members` 的人。
  - `access_version` 是请求人自己的权限版本（10.2）。
- `PATCH /api/v1/workspaces/{ws}` `{name?, archived?}`：改名、归档或重新打开，要 `manage_workspace`。归档期间不能修改的范围和 v0 相同：提交、上传、改设置、发言都返回 `409 archived`；读取、拉取、实时通道和成员管理照常。
- `POST /invite/reset`：重置邀请码，返回 `{invite_code}`，要 `manage_members`。

### 5.2 成员

- `GET /members`：`[{id, nickname, roles, joined_at}]`，所有成员都能读。`roles` 不含基础身份 `member`。
- `PATCH /members/{id}` `{nickname?, roles?}`：
  - `nickname` 只能改自己的。
  - `roles` 是新的完整列表。按 4.5，要能管理这个成员（`CanManageMember`），而且加上和去掉的每个身份，都要排在自己下面。
- `DELETE /members/{id}`：移出成员，要能管理他。成员也可以这样移出自己，即退出工作组，这是安全权利，任何设置都关不掉；只有组长不能退出，要先转让，否则返回 `409 leader_must_transfer`。
- `POST /leader` `{member}`：组长把组长转给另一个成员，只有组长能调。原组长变成普通成员，保留原来的其他身份。组长丢了手机时，由服务端管理员用命令行转让。

### 5.3 设备

- `GET /members/{id}/devices`：`[{id, device, created_at, last_seen_at}]`。本人和能管理他的人可以读。
- `DELETE /devices/{id}`：吊销一台设备的令牌，本人和能管理设备主人的人可以操作。那台设备的实时连接立即以 `4401` 断开。
- `POST /members/{id}/transfer-code`：生成一次性的转移码，返回 `{code, expires_at}`。只有本人和组长能生成：本人换手机时在旧手机上生成；手机丢了，由组长代为生成。别人不能生成，否则就能冒充这个成员。转移码 12 位，用的字符和邀请码一样，不区分大小写，输入时可以带空格和 `-`；10 分钟内有效，只能用一次，新生成的会让这个成员之前没用过的作废；生成和使用都记进操作日志，并通知这个成员的其他设备。
- 新手机拿转移码调用 `POST /api/v1/join` `{transfer_code, device}`，得到同一个成员的新令牌，身份和自己建的行都不变（3.4）。

### 5.4 身份

- `GET /roles`：`[{id, name, position, permissions, version}]`，所有成员都能读。基础身份的 `id` 固定是 `member`，位置固定是 0。
- `POST /roles` `{name, position, permissions}`：新建身份，返回新身份，要 `manage_roles`。`position` 必须低于自己的级别，大于 0；`permissions` 里的每一项都要自己能授出（4.5）。
- `PATCH /roles/{id}` `{name?, position?, permissions?, base_version}`：修改身份，要能管理这个身份（`CanManageRole`），新的 `position` 也要低于自己的级别；改到的权限要能授出。基础身份只能改 `permissions`，而且只有组长能改：每个人都有基础身份，包括排在修改人上面的人（和 5.5 的覆盖一样）。`base_version` 和当前的 `version` 不同时，返回 `409 stale`，带上当前的身份。
- `DELETE /roles/{id}`：删除身份，要能管理它。基础身份不能删（`400 invalid`）。删掉后，成员身上的这个身份一并去掉，图层覆盖里的也一并删除。
- `permissions` 里的值按 4.2：`edit_rows`、`delete_rows` 取 `"none"`、`"own"`、`"all"`，其余取 `true` / `false`；不认识的权限名返回 `400 invalid`。

### 5.5 图层覆盖

- `GET /layers/{layer}/overrides`：`{<身份 ID>: {view_layer?, edit_rows?, delete_rows?}}`，所有能看到这个图层的成员都能读。
- `PUT /layers/{layer}/overrides/{role}` `{view_layer?, edit_rows?, delete_rows?}`：整体替换这个身份在这个图层上的覆盖，空对象表示去掉覆盖。要能管理这个身份；每一项的值都不能高于自己在全局的那一档（和给身份授权一样，4.5）。基础身份 `member` 上的覆盖对所有人生效，包括排在设置人上面的人（4.4），所以只有组长能设。

### 5.6 共享图层

- `POST /layers` `{id, name, geometry_type, crs, fields, style?, form?, order?}`：新建共享图层，要 `manage_layers`。`id` 是客户端生成的 UUID；同一个 `id` 已经建过、结构也相同时返回原来的图层（重试安全），结构不同时返回 `409 stale`。新图层的 `schema_version` 是 1（7.1）。
- `DELETE /layers/{id}`：删除共享图层，要 `manage_layers`。图层行记为已删除（墓碑），它的行和附件行都留着，`POST /layers/{id}/restore` 可以恢复。删除和恢复都会让图层行出现在拉取结果里（8.2），带上 `deleted`；客户端看到 `deleted: true` 就在本地隐藏这个图层和它的行，其中待上传的修改按 4.6 标为"未能提交"。删除后它的行不再出现在拉取结果里，提交到它上面的修改返回 `unknown_layer`。
- **本地工程加入工作区**：客户端先按上面的接口把本地的每个图层建到服务端（`id` 不变），再把行当作新行，按 8.1 分批提交，附件按第 9 节上传。中途断了，按同样的 `id` 重来即可。

### 5.7 变化的通知与日志

- 每次修改成员、身份或覆盖后，服务端在实时通道发 `members_changed`；实际权限因此变了的成员，`access_version` 加 1，并收到 `access_changed`（10.2）。
- 改权限、分配身份、移出成员、吊销设备、转让组长，都记进操作日志：`GET /audit?before=<id>&limit=100` 按时间倒序返回 `[{id, at, by, action, target, detail}]`，只有组长能读。日志不能修改，也不能删除。

## 6. 行与合并

### 6.1 行

- 每行属于一个图层，有全局唯一的 UUID，由创建它的客户端生成。
- 字段的键是图层结构里的字段 ID，不是字段名。几何是一个名为 `geom` 的字段，值是 GeoJSON 几何对象，坐标用图层的坐标系；几何整体算一个字段。
- 服务端为每个字段记四样东西：值、最后修改人、编辑时间（换算到服务端时钟，见 6.3）、最后修改它的序号 `seq`。
- 删除也按字段记：`deleted` 的值为 `true` 或 `false`。删除的行保留全部字段（墓碑），可以恢复。

### 6.2 提交一条修改

客户端每次只提交自上次同步以来改过的字段：

```json
{
  "row": "8d3c6f0e-0c1a-4d7e-9a43-3f1d9b0f4e21",
  "base_seq": 5,
  "client_now": "2026-11-25T12:00:00Z",
  "set": {
    "f1": { "value": "D001", "edited_at": "2026-11-25T11:50:00Z" },
    "geom": { "value": { "type": "Point", "coordinates": [114.0, 30.0] }, "edited_at": "2026-11-25T11:50:00Z" }
  },
  "delete": { "value": true, "edited_at": "2026-11-25T11:55:00Z" }
}
```

| 字段 | 说明 |
|---|---|
| `base_seq` | 客户端最后一次看到这一行时，服务端的序号；新建的行为 `0` |
| `client_now` | 发出请求时客户端的时钟；批量提交时写在请求顶层，对其中所有修改有效（8.1） |
| `set` | 改过的字段，各带新值和客户端记下的编辑时间；没改的字段不要带 |
| `delete` | 可选。`true` 删除，`false` 恢复；值不是布尔值的请求被拒绝 |

修改人由服务端按鉴权身份填写，不由客户端提供。批量提交的请求和响应见 8.1。

### 6.3 编辑时间

服务端把客户端的编辑时间换算到自己的时钟：

> 编辑时间（服务端）= 服务端收到请求的时间 −（`client_now` − `edited_at`）

换算结果晚于服务端当前时间的，按服务端当前时间算。

### 6.4 合并规则

服务端逐个字段处理 `set` 里的修改。字段的 `seq` 大于 `base_seq`，说明客户端修改之后别人也改过它，称为"并发修改"。

1. **没有并发修改**（服务端还没有这个字段，或它的 `seq` 不大于 `base_seq`）：直接采用新值。
2. **有并发修改，值相同**：不变，不算冲突。值按 JSON 比较，忽略格式和对象键的顺序。
3. **有并发修改，值不同**：编辑时间晚的为准；时间相同的，后到达服务端的为准。落败的值写进冲突记录（`value`）。
4. **字段已从图层删除**：这次修改写进冲突记录（`deleted_field`），其余字段照常处理。

删除和恢复：

5. **删除**：`base_seq` 之后没有任何字段被改过，才删除；否则不删，删除写进冲突记录（`delete_rejected`），提示删除的人。
6. **别人删除了这一行**（删除发生在 `base_seq` 之后），而这次修改改了字段：字段照常合并，这一行恢复，那次删除写进冲突记录（`delete_overridden`），提示删除的人。恢复记在这次修改名下：修改人是提交者，时间是服务端收到请求的时间，序号是这次修改的序号。
7. **恢复**：已删除的行，`delete` 为 `false` 时恢复。

### 6.5 冲突记录

```json
{ "kind": "value", "field": "f1",
  "kept": { "value": "from m2", "by": "m2", "at": "2026-11-25T11:30:00Z", "seq": 9 },
  "lost": { "value": "from m1", "by": "m1", "at": "2026-11-25T11:00:00Z", "seq": 7 } }
```

| `kind` | 什么时候 | `lost` 是 |
|---|---|---|
| `value` | 规则 3 | 落败的值（可能是服务端原来的值，也可能是这次提交的值） |
| `deleted_field` | 规则 4 | 这次提交的值 |
| `delete_rejected` | 规则 5 | 这次提交的删除 |
| `delete_overridden` | 规则 6 | 别人的那次删除 |

- 一次修改产生的冲突，先按字段 ID 排序列出字段冲突，再列删除冲突。
- 有未处理冲突的行标为"有冲突"。组长或当事人可以一键换成另一个值；换值就是一次普通修改，按同样的规则合并。

### 6.6 共用测试样例

合并规则的测试样例在 [`protocol/testdata/merge/cases.json`](../testdata/merge/cases.json)，服务端（`server/internal/merge`）和安卓客户端都必须逐条通过。每条样例给出服务端当前的行、一次修改和期望的结果；服务端当前时间、序号和图层现有字段取文件开头的默认值，个别样例另行指定。

服务端另有随机交错测试：几个时钟不准的客户端交替离线修改、删除、恢复和提交，检查任何一次提交的值要么进了行，要么进了冲突记录。

## 7. 图层与结构变更

### 7.1 图层

图层本身也是一行，属于系统表 `layers`，有全局唯一的 UUID。它的属性分两类：

- **按第 6 节合并的字段**：`name`（名称）、`style`（样式，JSON，见 [ADR 0006](../../docs/adr/0006-rendering-and-styles.md)）、`form`（表单布局，JSON）、`order`（图层顺序，数字）。可以离线改，和普通行的字段一样合并。`style` 和 `form` 各自整体算一个字段：两人同时改了样式的不同部分，也按同一字段处理，落败的那份进冲突记录。
- **结构**：几何类型 `geometry_type`、坐标系 `crs`、字段定义 `fields` 和结构版本 `schema_version`。只能在线改，见 7.3。

| 结构 | 说明 |
|---|---|
| `geometry_type` | `Point`、`LineString`、`Polygon`、`MultiPoint`、`MultiLineString`、`MultiPolygon`，或 `None`（没有几何的表）。创建后不能改 |
| `crs` | 创建时定，`EPSG:代码` 或 WKT2 文本；创建后不能改，要换坐标系就新建图层再导入。几何坐标按这个坐标系，轴顺序一律东、北（经度、纬度） |
| `fields` | 字段定义的列表，见 7.2 |
| `schema_version` | 结构版本，从 1 开始，每次结构变更加 1 |

共享工作区里的图层要在线创建：创建请求带上初始结构，`schema_version` 为 1。离线时只能在本地工程里建图层，本地工程加入工作区时再上传，接口见 5.6。

### 7.2 字段

```json
{ "id": "f3k9x2", "name": "岩性", "type": "string", "options": ["花岗岩", "灰岩"] }
```

| 属性 | 说明 |
|---|---|
| `id` | 由新增字段的一方生成，1 至 64 个字符（字母、数字、`_`、`-`），在图层内唯一，删除后也不再使用。行里的字段用它作键（第 6 节）。`geom` 留给几何，不能用 |
| `name` | 显示名，可以改；改名不影响已有数据，也不影响合并 |
| `type` | 见下表；创建后不能改 |
| `options` | 可选。取值列表，界面上显示成选择框 |

| `type` | JSON 中的值 |
|---|---|
| `string` | 字符串 |
| `integer` | 整数，范围 ±(2^53 − 1)：超出这个范围时很多 JSON 解析器会丢精度，更大的编号请用 `string` |
| `real` | 数字 |
| `boolean` | `true` 或 `false` |
| `date` | 字符串，`2026-11-25` |
| `datetime` | 字符串，RFC 3339，例如 `2026-11-25T11:50:00Z` |
| `json` | 任意 JSON 值 |

任何类型的值都可以是 `null`，表示没有填。

### 7.3 结构变更

```
POST /api/v1/workspaces/{ws}/layers/{layer}/schema
```

```json
{
  "base_version": 3,
  "ops": [
    { "op": "add_field", "field": { "id": "f7q2m1", "name": "采样编号", "type": "string" } },
    { "op": "rename_field", "id": "f3k9x2", "name": "岩石名称" },
    { "op": "set_options", "id": "f3k9x2", "options": ["花岗岩", "灰岩", "砂岩"] },
    { "op": "delete_field", "id": "f1a8z0" }
  ]
}
```

- 只能在线做。服务端的 `schema_version` 不等于 `base_version` 时返回 409 `stale`，带上当前结构；客户端更新本地结构后，让用户在新结构上重做。
- 一次请求里的操作按顺序执行，要么全部成功，要么一个都不做。成功后 `schema_version` 加 1，响应带新的结构。
- 字段类型、`geometry_type` 和 `crs` 都不能改。要换字段类型，就新增一个字段、迁移数据、再删掉旧字段。
- 删除字段：行里不再返回这个字段，旧值留在服务端的历史里；之后对它的修改进冲突记录（6.4 规则 4）。
- 改结构需要 `edit_schema` 权限，见第 4 节。

### 7.4 离线的客户端

- 离线时只能改数据和 7.1 里按字段合并的属性，不能改结构。
- 客户端按它知道的结构提交，服务端按当前结构合并：字段改名不影响；客户端不知道的新字段，它自然不会提交；已删除字段上的修改进冲突记录。
- 客户端拉取到更高的 `schema_version` 时，更新本地结构。

## 8. 提交、拉取与冲突处理

### 8.1 提交

```
POST /api/v1/workspaces/{ws}/rows
```

```json
{
  "client_now": "2026-11-25T12:00:00Z",
  "changes": [
    { "id": "c2b1…", "layer": "4f0e…", "row": "8d3c…", "base_seq": 5,
      "set": { "f1": { "value": "D001", "edited_at": "2026-11-25T11:50:00Z" } } }
  ]
}
```

- 每条修改就是 6.2 的格式，再加上客户端生成的修改 ID `id`（UUID）和所在图层 `layer`。`client_now` 写在请求里，对其中所有修改有效。
- 单次最多 `max_push_batch` 条（见 3.3），同一请求里同一行只能出现一次。
- 服务端在一个事务里逐条处理，每条接受的修改分配一个新的 `seq`。响应和请求一一对应：

```json
{
  "results": [
    { "id": "c2b1…", "status": "applied", "seq": 18, "conflicts": [] },
    { "id": "77ab…", "status": "duplicate", "seq": 12 },
    { "id": "5e10…", "status": "rejected", "error": "invalid_value", "message": "f2 must be an integer" }
  ],
  "seq": 18
}
```

| `status` | 含义 | 客户端处理 |
|---|---|---|
| `applied` | 已按第 6 节合并，`conflicts` 列出这次产生的冲突（可能为空） | 标为已同步；有冲突就提示用户 |
| `duplicate` | 这个修改 ID 已经处理过（重试），返回当时的 `seq`。修改 ID 和修改历史保存一样久，客户端不能重复使用 | 标为已同步 |
| `rejected` | 格式或权限不对，这条修改没有生效；`error` 是机器码 | 留在本地，提示用户 |

`rejected` 的机器码：`unknown_layer`（图层不存在）、`invalid_value`（值和字段类型不符，或 `delete` 不是布尔值）、`forbidden`（没有权限）、`archived`（工作区已归档）。不在这里的问题（请求本身格式不对、批次过大）按整个请求出错，返回相应的状态码。

### 8.2 拉取

```
GET /api/v1/workspaces/{ws}/changes?since=17&limit=500
```

返回 `seq > since` 的变化，按 `seq` 升序：

```json
{
  "layers": [ { "id": "4f0e…", "schema_version": 4, "fields": [ … ], "name": { "value": "地质点", "by": "m1", "at": "…", "seq": 20 } } ],
  "rows": [
    { "layer": "4f0e…", "id": "8d3c…", "conflicted": true,
      "fields": { "f1": { "value": "D001", "by": "m2", "at": "2026-11-25T11:50:00Z", "seq": 18 } },
      "deleted": null }
  ],
  "conflicts": [
    { "id": "k91…", "layer": "4f0e…", "row": "8d3c…", "seq": 18, "resolved": false,
      "kind": "value", "field": "f1", "kept": { … }, "lost": { … } }
  ],
  "seq": 25,
  "more": false
}
```

- 行和图层都返回当前的完整状态，每个字段带 6.1 的四项信息；一行多次修改只返回最新状态。已删除的行也返回，带 `deleted`。
- `seq` 是下次请求应传的 `since`；`more` 为 `true` 时立即继续拉取。
- 客户端为每一行记下拉到它时的 `seq`，下次修改这一行就用它作 `base_seq`。这样在它之后别人改过的字段，`seq` 一定更大，服务端能认出是并发修改。
- `base_seq` 只在拉取到这一行的新状态时更新，不能用提交返回的 `seq`：那之前别人可能改过客户端还没拉到的字段，用提交的 `seq` 作基准，这些修改就不再算并发，会被悄悄覆盖。
- `conflicts` 包括新产生的冲突，也包括状态变了（比如被处理了）的冲突。
- 可选参数 `layers=<图层 ID>,<图层 ID>…` 只拉这些图层的行、附件行和冲突，用于权限变化后补拉新看到的图层（10.4）。这样拉到的 `seq` 只用于继续这次补拉，不能当作全局的 `since` 保存。

### 8.3 处理冲突

```
POST /api/v1/workspaces/{ws}/conflicts/{id}/resolve
{ "choose": "lost" }
```

- `choose` 是 `kept`（保留现在的值，只把冲突标为已处理）或 `lost`（换成落败的那个值）。
- 选 `lost` 时，服务端以处理人的名义做一次普通修改，以冲突产生时的 `seq` 作 `base_seq`，按第 6 节合并；这期间如果字段又被别人改过，就会产生新的冲突，不会悄悄覆盖。
- 冲突处理完后，所在行没有其他未处理冲突时，`conflicted` 变为 `false`。
- 谁能处理冲突：组长，以及冲突两边的当事人。这不是一项可以分配的权限：除这三方之外，谁也不能替别人选（第 4 节）。

### 8.4 推荐的客户端同步流程

1. 本地每次修改：记下改了哪个字段、新值和编辑时间，标为"待上传"；同一字段多次修改只保留最后一次。
2. 先上传修改引用的附件缩略图（9.3），再分批提交待上传的修改，每条带上这一行的 `base_seq` 和一个修改 ID；重试时用同一个修改 ID。
3. 从上次保存的 `seq` 开始拉取，直到 `more` 为 `false`，用服务端的状态更新本地；本地仍有待上传修改的字段，保留本地的值。
4. 保存最新的 `seq`，有新冲突就提示用户。

## 9. 附件

照片、草图、录音、视频这些附件分成两部分：登记附件的**附件行**，和附件的**文件**本身。附件行和别的行一样同步、合并（[ADR 0008](../../docs/adr/0008-sync-and-merge.md)）；文件按内容寻址，单独分块上传，可以断点续传。

### 9.1 附件行

附件行属于系统表 `attachments`，有客户端生成的 UUID，按第 6 节合并。字段：

| 字段 | 说明 |
|---|---|
| `target_layer`、`target_row` | 附件挂在哪个图层的哪一行上，创建后不能改：要挪到别的行，就删掉再新建。改这两项的修改被拒（`invalid_value`）。手机上对应 GeoPackage 的关联表（[ADR 0004](../../docs/adr/0004-project-storage.md)） |
| `file` | 原文件的 SHA-256，小写十六进制 |
| `thumb` | 缩略图文件的 SHA-256；没有缩略图（比如录音）时为 `null` |
| `type` | 原文件的 MIME 类型，比如 `image/jpeg`、`audio/mp4` |
| `size` | 原文件的字节数 |
| `name` | 原文件名，只用于显示和导出 |
| `meta` | 其他信息，JSON，比如拍摄方位、时长；整体算一个字段 |

- 提交（8.1）和拉取（8.2）时，附件行外层的 `layer` 写固定的 `attachments`；挂在哪个图层写在 `target_layer` 字段里。
- 删除附件，就是把附件行的 `deleted` 设为 `true`，和删行一样可以恢复。
- 权限跟着它挂的那一行走：新建、修改、删除附件行，按对那一行做 `edit_rows` 判断（4.4）；能看到那个图层，才能看到它的附件：拉取时，看不到的图层上的行和附件行都不返回。

### 9.2 上传文件

文件按 SHA-256 存放，同一工作区里同样的文件只存一份。

**查询**：

```
HEAD /api/v1/workspaces/{ws}/files/{sha256}
```

已有返回 `200`，没有返回 `404`。

**开始上传**：

```
POST /api/v1/workspaces/{ws}/uploads
{ "sha256": "9f86…", "size": 4718592, "type": "image/jpeg" }
```

```json
{ "upload": "u_3kq…", "offset": 0, "chunk_size": 1048576 }
```

- 文件已经有了，返回 `200 { "exists": true }`，不用再传。
- 同一个成员对同一个文件已有没传完的上传，返回那一次的 `upload` 和已经收到的 `offset`，从那里接着传。所以客户端不用自己记 `upload`，应用重启后再调一次就能续上。
- 超过 `max_file_size`（3.3）返回 `413 too_large`。
- 需要在某个图层上有 `edit_rows`（至少 `own`）。

**传一块**：

```
PUT /api/v1/workspaces/{ws}/uploads/{upload}?offset=1048576
```

请求体是从 `offset` 开始的原始字节，不超过 `chunk_size`，加上之后也不能超过开始时声明的 `size`，否则返回 `400 invalid`，已收到的部分不变。

- `offset` 必须等于服务端已经收到的字节数，否则返回 `409 offset_mismatch`，带上正确的 `offset`，客户端从那里重传。
- 没传完时返回 `{ "offset": <已收到的字节数> }`。
- 收齐 `size` 字节后，服务端核对哈希：对得上返回 `201 { "sha256": "9f86…" }`；对不上返回 `400 hash_mismatch`，这次上传作废。
- 7 天没有动静的上传，服务端删掉已收到的部分。
- 上传已经完成或者已经作废，再往里传返回 `404 not_found`。比如最后一块的 `201` 响应丢了，客户端重传时就会这样；这时重新调用"开始上传"，文件已经有了就会得到 `exists: true`。

**下载**：

```
GET /api/v1/workspaces/{ws}/files/{sha256}
```

支持 `Range`，可以断点续传；`ETag` 就是哈希，可以长期缓存。只有引用这个文件的附件行里，至少有一条是请求人能看到的，才返回文件，否则返回 `404 not_found`。请求人能看到引用它的附件行、但文件还没传上来时，返回 `404 not_uploaded`。共享设置里引用的文件，所有成员都能下载。

### 9.3 先传缩略图

野外信号差，原图可能要很久才传得上去。为了让组里尽早看到照片：

1. 拍照后，客户端生成缩略图：JPEG，长边 640 像素。
2. 先传缩略图，再提交附件行（`file` 写原图的哈希，`thumb` 写缩略图的哈希），然后再慢慢传原图。客户端可以设成只在 Wi-Fi 下传原图。
3. 服务端接受原图还没传上来的附件行。别人拉到这样的附件行，下载原图得到 `404 not_uploaded`，就先显示缩略图，标上"原图未上传"。
4. 附件行引用的文件，包括已删除附件行引用的，服务端都不会当作无用文件清理；共享设置里引用的也一样。

### 9.4 客户端流程

8.4 的第 2 步具体是：先传各条修改引用的缩略图，再提交修改，最后在后台传原图。原图上传失败不影响同步，下次从断点接着传。

## 10. 实时通道

实时通道只做提醒和位置共享：数据本身一律按第 8 节拉取，通道断了也不丢东西。

### 10.1 连接

```
GET /api/v1/workspaces/{ws}/ws
```

- 用 WebSocket 连接，带 `Authorization: Bearer <令牌>`。设不了请求头的客户端（比如浏览器），改用查询参数 `?access_token=<令牌>`；服务端不能把这个参数写进访问日志。
- 消息都是 JSON 文本帧，带 `type` 字段。不认识的 `type` 直接忽略（3.1）。
- 服务端每 30 秒发一次 WebSocket ping 帧。处理不了协议帧的客户端，可以用应用层的 `ping` / `pong` 消息。
- 断线后，客户端隔一段时间重连，间隔逐次加倍，最长 1 分钟，再加一点随机抖动。重连后先拉取一次（8.2），补上断线期间的变化。
- 令牌被吊销或成员被移出时，服务端用关闭码 `4401` 关闭连接，客户端不要重连。`4400`–`4499` 留给协议以后用。

### 10.2 消息

| `type` | 方向 | 内容 |
|---|---|---|
| `hello` | 服务端→客户端 | 连上后的第一条：`{member, seq, access_version, online, positions}`。`seq` 是服务端当前的序号，比本地保存的大就去拉取；`access_version` 是这个成员权限的版本，他的实际权限每变一次就变一次，和本地保存的不同就按 10.4 处理；`online` 是在线成员的 ID；`positions` 是最近 15 分钟里每人最后的位置，只发给有 `view_locations` 的人 |
| `changes` | 服务端→客户端 | `{seq}`：有新的变化，客户端随后拉取。连续的变化可以合并成一条 |
| `access_changed` | 服务端→客户端 | 收到这条的成员，自己的权限变了（身份、身份的权限或图层覆盖），见 10.4 |
| `members_changed` | 服务端→客户端 | 成员、身份有变化，客户端重新读取成员和身份列表 |
| `settings_changed` | 服务端→客户端 | `{version}`：共享设置变了，客户端重新读取 |
| `workspace_changed` | 服务端→客户端 | `{name, archived_at?}`：工作区改名、归档或重新打开 |
| `presence` | 服务端→客户端 | `{member, online}`：成员上线或下线 |
| `position` | 双向 | 见 10.3 |
| `position_stop` | 双向 | 停止共享位置，见 10.3 |
| `ping` / `pong` | 双向 | 保活 |
| `error` | 服务端→客户端 | `{error, message}`：客户端发来的消息有问题，比如 `bad_json`；连接不断 |

### 10.3 位置共享

客户端发：

```json
{ "type": "position", "lon": 116.39, "lat": 39.91, "alt": 52.0, "accuracy": 4.5, "heading": 90, "speed": 1.2, "at": "2026-11-25T12:00:00Z", "client_now": "2026-11-25T12:00:01Z" }
```

- 坐标是 GNSS 给出的 WGS84 经纬度（EPSG:4326），和图层的坐标系无关；`alt` 是椭球高，单位米。
- 开不开位置共享是每个人自己的事，属于安全权利（4.2），任何设置都关不掉，也不能替别人打开。
- 服务端补上 `member`，并像 6.3 那样用 `client_now` 把 `at` 换算到服务端时钟，然后转发，只发给有 `view_locations` 的在线成员；没有这项权限的人连别人的位置都收不到。
- 成员刚得到 `view_locations` 时，服务端随 `access_changed` 之后把当前的位置（和 `hello` 里的一样）发给他。
- 关掉位置共享时，客户端发 `{ "type": "position_stop" }`。服务端立即删掉他缓存的位置，并把 `{ "type": "position_stop", "member": … }` 转发给有 `view_locations` 的人，对方从地图上去掉他。断线超过 15 分钟的，缓存的位置也会过期。
- 每个成员每秒最多一条，多出来的直接丢掉；坐标超出范围的也丢掉。
- 位置只在服务端内存里放一会儿，不写进数据，服务端重启就没了。要长期保存，客户端把轨迹作为行提交。

### 10.4 权限变化后

成员的权限变了以后，他能看到的图层可能跟着变，而按 `since` 增量拉取不会带回原来就有、只是之前看不到的行。所以收到 `access_changed` 后，或者重连时发现 `hello` 里的 `access_version` 和本地保存的不同，客户端：

1. 重新读取自己的权限。
2. 删掉本地已经看不到的图层上的行和附件行；其中还有待上传的修改，按 4.6 标为"未能提交"，不删。
3. 对新看到的图层，带上 `layers` 参数从 `since=0` 补拉（8.2），直到 `more` 为 `false`；平时的增量拉取照旧用原来的 `since`。
4. 都做完后，保存新的 `access_version`。中途断了，下次连上还会再做一遍。
